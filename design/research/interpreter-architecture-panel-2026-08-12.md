## Value word layout (tagging scheme) [strong]
Use a 16-byte two-word tagged value (K-style fat value), NOT NaN-boxing: word 0 = 8-byte payload (i64 / f64 / char codepoint / u32 symbol-id / u32 word-id / 8-byte heap pointer), word 1 = tag + flags. In Rust this is a niche-optimized enum: Int(i64), Float(f64), Char(u32), Symbol(SymId), Word(WordId), List(*Header), Dict(*Header), Task(*Header). All atoms live fully inline — no heap allocation ever for ints, floats, chars, symbols, or words; heap pointers only for lists/dicts/tasks. Reject NaN-boxing decisively: NaN-boxing (as in CBQN and JS engines) reserves the low 48-51 bits for non-float payloads, which cannot hold ecl's full-range int64 — ecl's decision 4 makes int64 a real semantic type with overflow-as-error at 2^63, so NaN-boxing would force heap-boxing large ints or corrupting int semantics. NaN-boxing pays off when 'number' means f64 (BQN, JS); ecl is not that language. The 2x stack-bandwidth cost of 16-byte values is irrelevant under the ledger's own performance model (decision 21c: per-token dispatch never needs to be fast; kernels over flat leaves are the surface). Reject low-bit pointer tagging too: it steals bits from int64 the same way. Data stack = plain Vec<Value> of these 16-byte cells.
GROUNDING: CBQN src/README.md documents its 64-bit NaN-boxed value B ('top 16 bits' tag, 'low 48 bits are a Value*') — workable there because BQN numbers ARE f64; ecl's true int64 breaks this. K (k4/kdb+ and Whitney's ksimple) uses pointer-to-header objects with type in the header, i.e. fat tagged objects, not NaN-boxes; ksimple stores type/length/refcount in the words before the data pointer. The 'Float Self-Tagging' paper (arXiv 2411.16544) surveys the tagging trade space and confirms tagged-union vs NaN-box is a payload-width tradeoff. Rust enum-with-niche gives the 16-byte layout for free.

## Heap object header layout [strong]
One fixed 16-byte header preceding every heap payload: { rc: AtomicU32; meta: u32 = type tag (5 bits: generic-spine / leaf-i64 / leaf-f64 / leaf-char1 / leaf-char2 / leaf-char4 / leaf-symbol / dict / task), bucket-class (6 bits, log2 of allocation size), flags (shared-across-units bit + reserved biased-RC owner byte); len: u64 }. Do NOT store capacity: capacity is derived from the bucket class minus header size, exactly as kdb+ derives it from the power-of-two block — this is what makes 'slack capacity' a free consequence of the allocator rather than a second bookkeeping field. Specialization (which leaf kind a list is) is a header fact set at construction, never recomputed by inspection. Width tag for char leaves (1/2/4 bytes per codepoint) lives in the type tag per PEP 393, giving O(1) codepoint indexing and 1 byte/char for ASCII strings as decision 15 requires. Add leaf-symbol (u32 ids) to the leaf set — K has symbol vectors, the skeleton's printer already treats symbol lists as specialized, and interned u32 ids make it a natural flat leaf; the ledger's leaf enumeration (i64/f64/chars) should be amended to include it.
GROUNDING: kdb+ memory docs (TimeStored 'Memory Management in Kdb', DefconQ, Data Intellect): vectors go in next-power-of-two blocks with header included, capacity implicit in block size; 'kdb uses a variant of the buddy memory system using reference counting'. ksimple (kparc/ksimple): length and refcount stored in words before the data pointer. PEP 393: three string kinds (UCS-1/2/4) chosen per-string by widest codepoint. CBQN: type + refcount in a common Value header, shape/ia fields for arrays.

## Reference counting: precise counts, atomic in v1, biased/promotion as the designed evolution [strong]
Precise reference counts, not a sharing bit. A sticky shared-bit is one-way — a value dup'd once then popped would be pessimized forever, defeating the CoW guarantee's 'copy once, then cheap' clause; K, Swift, and Perceus all use true counts precisely because rc==1 is the reuse trigger and counts recover uniqueness when references die. The ledger's Runtime section says 'refcount or shared bit' — strike the 'or shared bit' option. ATOMICITY: because decision 20 guarantees immutable values cross unit boundaries with no copying or serialization, and units run truly parallel, any object may end up touched by two threads — so v1 ships plain atomic RC (Relaxed increments, Release/Acquire decrement, i.e. Rust Arc discipline / Swift's model). This is sound, simple, and its cost is contained by the coarse-kernel model: a kernel call does O(1) RC ops on list headers, never O(n) per-element ops, because leaf elements are unboxed. Reserve in the header (flags + owner byte) the two known escape hatches for later, without relayout: (a) biased RC per Choi/Shull/Torrellas — two counters, owner thread non-atomic, ~2x faster RC ops, 22.5% mean exec-time reduction measured in Swift; (b) BEAM-refc-binary-style escape promotion — values are unit-local (non-atomic RC) until they cross the enumerable send points (spawn's cons'd quotation, task outcome cells), where a spine walk sets the shared flag and switches those nodes to atomic ops; the walk touches only headers (leaves are flat), so it is O(spine) not O(data). Full BEAM copy-on-send is ruled out by the ledger's no-copy claim.
GROUNDING: Choi, Shull, Torrellas, 'Biased Reference Counting: Minimizing Atomic Operations in Garbage Collection' (PACT 2018, iacoma.cs.uiuc.edu/iacoma-papers/pact18.pdf): owner-biased dual counters, implemented in Swift runtime, 22.5% avg client exec-time reduction. Erlang Efficiency Guide (erlang.org/doc/system/binaryhandling): binaries >64 bytes are refc binaries on a shared heap with a reference counter, referenced from per-process ProcBins — the named precedent for shared-immutable-with-RC across share-nothing processes. Swift isKnownUniquelyReferenced (Swift stdlib docs, forums.swift.org discussions): uniqueness probe against a true atomic count. Whitney (ACM Queue 'A Conversation with Arthur Whitney'): 'everything is reference counted... when it's free you know immediately and get good reuse'.

## CoW/uniqueness interaction with the stack machine: ownership discipline (Perceus-on-a-stack) [strong]
Make the data stack own its values: pushing transfers ownership, popping transfers it to the primitive — a plain push/pop does ZERO RC operations. The dup-family (dup/over/pick/tuck) is the sole increment site in the evaluator; primitives consume their stack arguments and only increment when they store a reference into a new structure (list inclusion) or the env (binding). This is exactly Perceus's precise/ownership-passing discipline mapped onto a stack machine, and it is what makes uniqueness detection actually fire: after `1 append` on a vector built in a pipeline, rc really is 1 and the append goes into slack in place. Uniqueness test = atomic load of rc == 1 with acquire ordering (Swift semantics). Two corollaries: (a) in-place amend below the root requires rc==1 along the whole path (nested CoW, as in Swift arrays-of-arrays); check per level and copy the first shared node. (b) Kernels take borrowed views of arguments where possible (no rc traffic at all for read-only args like the left side of `at`), matching Perceus's borrowing refinement — cheap to do in Rust since &Header is a borrow the type system already tracks.
GROUNDING: Reinking, Xie, de Moura, Leijen, 'Perceus: Garbage Free Reference Counting with Reuse' (PLDI 2021, dl.acm.org/doi/10.1145/3453483.3454032): precise RC where cycle-free programs are garbage-free; reuse analysis turns functional updates into in-place mutation when rc==1; borrowing avoids counting read-only uses. Whitney's K: 'when doing a vector operation and the reference count is one, the vector can be reused' (ksimple docs / Whitney interview). Swift CoW: isKnownUniquelyReferenced before mutation, per-level for nested containers.

## Acyclicity: plain RC is complete — with one documented pathological exception [strong]
Ship no cycle collector, and never plan one. The argument, stated precisely so it can be defended: ecl values are immutable after construction and construction is bottom-up (a list can only contain values that already exist), so the value heap is a DAG by construction — the classic Erlang-term argument. The usual cycle-makers are all absent by ledger decree: no closures (decision 6 — a quotation is a plain list of atoms, and a word occurrence is a SYMBOLIC reference resolved through the env/registry at execution time, never a heap pointer, so recursive and mutually-recursive definitions create no heap cycles); no mutable cells; no amend. Two mutable indirections exist OUTSIDE the value heap and must be handled by policy, not by a collector: (1) env/registry tables — these are session-lifetime structures torn down explicitly, and binding replacement just decrements the old value; they hold values but values never hold envs (bindings resolve by name), so no cycle. (2) Task outcome cells, the single write-once mutable location: a spawned quotation can look up (via an env name) its own task handle and return it, making the cell's value contain the cell — a genuine RC leak. Rule: document it as a bounded leak (one task cell + its outcome), do not build machinery for it; alternatively have `await` cache the outcome and drop the cell's strong self-edge by storing outcomes weakly from handle to cell — but the documented-leak ruling is the K-spirited answer. Perceus's guarantee ('cycle-free programs are garbage free') applies to the entire language surface except this one corner.
GROUNDING: Perceus (PLDI 2021) is explicitly conditioned on cycle-freedom and names immutable functional data as the domain where RC alone is complete. Erlang/BEAM: per-process heaps of immutable terms need no cycle collector; the shared refc-binary heap is pure RC (Erlang Efficiency Guide) — sound because binaries are acyclic immutable data, the same property ecl values have. CPython, by contrast, needs its gc module precisely because it has mutable containers — the absence ecl guarantees.

## Bucket/slab allocation for slack capacity [settled-practice]
Adopt kdb+'s scheme nearly verbatim: power-of-two size classes from 16 B up to a large-slab threshold (kdb+ uses 64 MB), per-class free lists, larger blocks split buddy-style on miss, allocations above threshold go straight to mmap/system. A vector's capacity is its bucket size minus header; append writes into that slack while rc==1 and bumps len; growth reallocates into the next class — geometric doubling and therefore amortized O(1) append fall out of the size-class structure with no separate growth policy. Free lists should be per-unit (thread-local) with a global reservoir, so allocation needs no lock in the common case — this composes with share-nothing units (a block freed by a different unit than allocated it goes to the reservoir; BEAM and mimalloc both solve remote-free this way). For v1 in Rust, implement the size-class layer directly (it is ~200 lines) rather than riding the system allocator: the bucket class byte in the header is load-bearing for capacity derivation, so the allocator and the value representation are one design, as they are in K.
GROUNDING: kdb+ internals (TimeStored 'Memory Management in Kdb', DefconQ 'Memory Management', Data Intellect 'kdb+ is Memory Hungry, Right?'): power-of-two bins 16 B–64 MB, per-class freelists, recursive slab splitting, buddy variant with refcounting; a 64,000-byte vector occupies a 65,536-byte block — the slack IS the append headroom. CBQN src/README.md: buddy allocator modes (MM=1 'buddy', MM=2 '2buddy') as the production configuration of a modern array interpreter.

## Symbol interning [settled-practice]
One global, process-wide, append-only intern table: symbol = u32 index; the table is a Vec<Arc<str>> (or arena of bytes) plus a hash index; lookups on the hot path are integer loads, equality is u32 compare, dict-key hashing of a symbol hashes the id. Symbols are never freed (append-only), which is both K's and Erlang's ruling and what makes cross-unit sharing trivial: ids are plain data, valid in every unit, no promotion needed at spawn boundaries. Concurrent interning (units can call `parse`/`to-symbol`) needs an RwLock or sharded map on the WRITE path only; reads index the append-only vector without locking. Word atoms (decision 22: words ≠ symbols) share the same intern table with a distinct value tag — same u32 id space, different tag, so `to-word`/`to-symbol` are tag flips. Ordering (`<` on symbols, if allowed) goes through the table lazily; equality and hashing never do.
GROUNDING: kdb+ interns all symbols permanently in a global table (code.kx.com guidance on symbol cardinality exists precisely because interning is forever); Erlang's atom table is global and not garbage collected (Erlang Efficiency Guide) — both are the named precedents that append-only global interning is the correct cost model for a language where symbols are the idiomatic keys. ksimple: symbols as interned monotone ids.

## Dict representation (insertion-ordered, any-value keys) [strong]
CPython 3.6 / PyPy compact ordered dict, adapted: a dense entries leaf (parallel or interleaved arrays of key Value, value Value, cached u64 hash) in insertion order, plus a sparse index table of variable-width slots (u8 up to 128 entries, then u16, u32) holding offsets into the entries array. Insertion order is preserved by construction (decision 17), iteration is a linear walk over dense memory (which is exactly the dict-of-column-vectors table story — columns iterate like leaves), and the index table is a throwaway that rebuilds on copy. Any-value keys are fine because every ecl value is immutable and hashable: implement one structural hash kernel that walks spines iteratively and hashes flat leaves as memory runs (with the char-width and int/float-equality caveats: hash must agree with `=`, so 2 and 2.0 need the same hash — hash numerics by their f64 image when integral, per CPython's number-hash unification). Cache each key's hash in the entry: this turns decision 22's order-insensitive dict equality into O(n) probe-by-hash instead of the skeleton's O(n²) nested scan. Below ~8 entries, skip the index table and linear-scan the entries — small-dict dominance is the same observation that motivated CPython's split/compact designs.
GROUNDING: Raymond Hettinger's compact-ordered-dict design (python-dev, December 2012: 'More compact dictionaries with faster iteration'), shipped in CPython 3.6 — dense entries array + sparse variable-width index array (u8/u16/u32, -1 empty), insertion-ordered by design; PyPy blog 'Faster, more memory efficient and more ordered dictionaries' (Jan 2015) validated the same layout independently. CPython also demonstrates the hash-must-agree-with-equality rule across numeric types.

## Provenance (source spans) must leave the value word [strong]
Do not carry a span field in the runtime Value. Provenance is a reader/code-plane concern: attach spans only to code lists — either as a side table keyed by (list identity, element index) owned by the word's stored body, or as an optional trailing segment in the list header of reader-produced lists — and let the frame machine thread the current span for error dicts (decision 19) from the code it is executing, never from data values. A span on every value doubles (or worse) the value size, poisons leaf specialization (a leaf can't carry per-element spans anyway, so the skeleton's design already silently drops provenance on any future specialized path), and puts an Arc<str> clone on every value construction. The error-dict trace requirement is fully satisfied by code-plane provenance plus the frame machine's word trace.
GROUNDING: Every production interpreter in the reference set separates the two planes: CPython attaches line tables to code objects, not to objects; BEAM keeps line info in beam files/stack traces, not in terms; K carries no provenance on values at all. The skeleton itself demonstrates the cost: Value = ValueKind + Option<SourceSpan> makes the smallest int roughly 56 bytes.

===== AREA: dispatch =====

## Code representation: canonical value list + lazily derived, cached per-quotation execution view [strong]
Keep the immutable value list as the ONLY semantic representation ('body, cons, compose, each-over-code all operate on it), and derive a flat execution view per quotation, built lazily on first execution and memoized in the list's heap header. The view is an array of pre-classified entries: PushConst(index into a constants slice), CallWord(interned symbol id, call-site index), plus a parallel side-table of source spans. The view stores value-intrinsic facts only: word-vs-literal is a property of the atom itself (decision 22: words are distinct atoms), so classification never touches the environment. The late-binding claim in the task is CORRECT with three caveats the design must state explicitly: (1) the view must not pre-classify any word as 'primitive' — the skeleton resolves the env chain first and falls back to primitives, so + is shadowable and primitive-ness is a resolution, not a token property; primitives must become ordinary core-env bindings whose payload is a primitive id/fn pointer. (2) The view must be env-independent, because the same quotation value can execute under different resolution envs (module home vs caller); symbols-only satisfies this. (3) 'Immutable therefore never invalidated' is true semantically but NOT at the representation level: decision 1/21(b) permits hidden in-place mutation of uniquely-held lists (append into slack), so the runtime must either clear the header's view slot on any in-place mutation or treat 'machine holds this list for execution' as a sharing point; the slot itself must be OnceLock-style thread-safe since units run truly parallel. Expected win is modest and that is fine: a quotation list is already flat per nesting level, so the view mostly eliminates the skeleton's per-token Value+span clone, string hashing, and RwLock'd env probe, and gives each call site a stable index for stage-2 inline caches.
GROUNDING: BQN's reference architecture compiles source to a deliberately simple stack bytecode executed by a plain VM, with all performance living in the runtime primitives (Lochbaum, 'The BQN virtual machine and runtime', mlochbaum.github.io/BQN/implementation/vm.html); Ertl & Gregg (JILP 2003) establish that efficient interpreters run over flat 'virtual machine' arrays rather than walking linked/boxed program structures; CPython's code objects with co_consts/co_names tables are the production pattern for constants+names split; decision 8 of the ledger itself notes build-new-then-rebind 'is what makes cache invalidation tractable'.

## Dispatch technique for the frame-machine inner loop [strong]
v1: a single match/switch inner loop in one function — ip and view slice in locals, frames pushed only at word calls, combinators, and unit boundaries; do NOT chase computed goto or tail-call dispatch now. Rationale: (a) the host skeleton is Rust, where computed goto does not exist in stable and guaranteed tail calls (`become`, RFC 3407) are a nightly experiment as of 2026; (b) the folklore that switch dispatch is ~2x slower than threaded code (Ertl & Gregg 2003, measured on early-2000s predictors) is largely obsolete — Rohou, Swamy & Seznec (CGO 2015) showed modern indirect-branch predictors (ITTAGE-class) make switch interpreters competitive; (c) CPython 3.14's musttail tail-call interpreter, after Nelhage's analysis exposed that the headline 10-15% was mostly an LLVM 19 computed-goto regression, settles at roughly 1-5% geomean over a healthy computed-goto build — a ceiling on what dispatch technique is worth even for a bytecode-bound language, and ecl is kernel-bound by design. Architecture hedge: give every opcode handler the uniform signature (machine, ip, view) used by wasm3 and upb so the loop can be mechanically converted to tail-call dispatch if Rust `become` stabilizes and profiling ever shows dispatch on the profile — wasm3 demonstrates the tail-call 'meta machine' keeps VM registers in real registers, and upb demonstrated the same pattern at 2+GB/s in C via [[clang::musttail]].
GROUNDING: Ertl & Gregg, 'The Structure and Performance of Efficient Interpreters', JILP 5 (2003), jilp.org/vol5/v5paper12.pdf; Rohou, Swamy, Seznec, 'Branch Prediction and the Performance of Interpreters — Don't Trust Folklore', CGO 2015, inria.hal.science/hal-01100647; Nelhage, 'Performance of the Python 3.14 tail-call interpreter', blog.nelhage.com/post/cpython-tail-call/ plus Ken Jin's correction ('I'm Sorry for Python's tail-calling Interpreter's Results', fidget-spinner.github.io/posts/apology-tail-call.html); wasm3 docs/Interpreter.md ('M3: A high performance WebAssembly interpreter'); Haberman, 'Parsing Protobuf at 2+GB/s: How I Learned To Love Tail Calls in C', blog.reverberate.org (2021); Rust explicit-tail-calls tracking issue rust-lang/rust#112788 (nightly-only, LLVM backend only); Bell, 'Threaded Code', CACM 16(6) 1973 as the origin of the alternative being declined for v1.

## Symbol interning and binding resolution on the hot path [settled-practice]
Intern all symbols/words to small integer ids at read time (global interner; ids stable for a session). Bindings resolve by id through the env chain; primitives are ordinary bindings in the root core env whose BindingKind carries a PrimitiveId or Rust fn pointer, executed directly — eliminating both the skeleton's string `match word { "dup" => ... }` primitive dispatch and its env-miss-then-string-fallback path (which also makes shadowing rules uniform: core is just the outermost env). Env reads must not take an RwLock per token: with share-nothing units, each unit owns its env chain; the shared pieces (module registry, core) should be read via snapshot/epoch structures, with the ledger's 'binding writes are observable events' implemented as a monotonic generation counter bumped on every def/let/module re-registration.
GROUNDING: Interned names + indexed name tables are universal production practice: CPython interns identifiers and dispatches LOAD_GLOBAL/LOAD_ATTR by index into co_names; Lua interns all strings (TString) so name equality is pointer equality; K's tiny interpreter keys everything off symbols as pointers (Whitney, ACM Queue 2009 interview describes the small, cache-resident interpreter philosophy). PEP 509 (dict version tag) is the named precedent for making namespace writes observable as a cheap monotonic version for later guards.

## How far quickening, inline caching, and superinstructions may go under 'no JIT, threaded/opcode arrays at most' [strong]
Draw the line at machine code, precisely: (ALLOWED, stage 2) per-call-site inline caches in the execution view — each CallWord site stores (generation, resolved binding ref); on execution, if the guard generation matches the current env generation the cached binding is used, else re-resolve and refill. This is Brunthaler's quickening/inline-caching-without-dynamic-translation and CPython PEP 659's adaptive specialization, and it preserves late binding OBSERVATIONALLY: a re-def bumps the generation, every stale cache heals on next execution, so 'redefinition heals callers' still holds — the cache is representation, not semantics. (ALLOWED, stage 2/3) static superinstructions: fused opcodes for measured-hot pairs/triples (push-const+add, dup+call, etc.) selected at interpreter build time, vmgen/Gforth style, plus Dyalog-style idiom recognition at view-build time (recognize whole phrases like the mask idiom or `0 (+) fold` and emit one kernel opcode) — this is phrase-level, array-language-proven, and pure opcode rewriting. (PROHIBITED by decision 21) dynamic superinstructions and selective inlining — Piumarta & Riccardi (PLDI 1998) and Ertl & Gregg's dynamic superinstructions work by memcpy'ing compiled machine-code fragments into new sequences at runtime; that IS machine-code generation and crosses the ledger's line, as does any template JIT. One caveat from CPython history: PEP 509's whole-dict version tags were eventually rescinded (PEP 699) in favor of per-site cache entries with finer keys — start with one coarse per-env (or global) generation, accept spurious invalidation, and only refine granularity if re-resolution shows up in profiles.
GROUNDING: Brunthaler, 'Efficient Interpretation using Quickening', DLS 2010, and 'Inline Caching Meets Quickening', ECOOP 2010 (up to 1.71x without a JIT); PEP 659 'Specializing Adaptive Interpreter' (CPython 3.11+, quickening + adaptive instructions + superinstructions); PEP 509 / PEP 699 (dict version-tag guards and their supersession); Ertl & Gregg vmgen superinstructions documentation (Gforth); Piumarta & Riccardi, 'Optimizing direct threaded code by selective inlining', PLDI 1998 (the technique being explicitly ruled out); Dyalog APL idiom recognition ('specially recognised phrases treated as individual tokens and executed with special code', course.dyalog.com/Interpreter-internals/).

## Stack caching (TOS in a register) [judgment-call]
Skip it, for v1 and probably forever. Ertl's stack caching pays when stack cells are machine-word-sized and dispatch-bound (Forth); ecl's Value is a multi-word refcounted tagged enum, the data stack must be snapshotable/discardable wholesale for unit rollback and attempt boundaries (a cached TOS register is extra state to spill at every frame operation, error unwind, and safe-point), and the cost model says stack traffic is amortized under kernels anyway. Keep the data stack a plain contiguous Vec with the top accessed through the natural last-element path; revisit only if a profile of real workloads shows push/pop as a top cost, which the K model predicts it will not be.
GROUNDING: Ertl, 'Stack Caching for Interpreters', PLDI 1995 (the technique and its assumptions: register-sized cells, dispatch-dominated workloads); Rohou et al. CGO 2015 (dispatch-side savings shrunken on modern hardware); Whitney ACM Queue 2009 / the K performance model as adopted verbatim by ledger decision 21 ('per-token dispatch never needs to be fast').

## Cost model and where the optimization budget goes (K philosophy, operationalized) [strong]
Adopt an explicit budget rule: the dispatch loop gets ONE design pass (view + interning + switch loop) and is then frozen; all subsequent performance work goes into the few dozen kernels over specialized flat leaves — pervasive arithmetic as monomorphic loops per (op, leaf-type) pair over i64/f64/char buffers, each/fold/scan/where/at/raze as single Rust loops that never re-enter the frame machine when the quotation argument resolves to a pervasive primitive or the data is a specialized leaf. This is exactly K's architecture (tiny cache-resident interpreter, fat flat primitives — 'K is fast because memcpy is fast'), the J incunabulum's shape (one page of dispatch, all substance in verbs over flat arrays), and CBQN's documented experience (a simple bytecode VM with essentially all performance in primitive implementations). Concretely for ecl: `(+) fold` over an i64 leaf must be one summation loop (idiom-recognized or kernel-dispatched), never n trips through Frame::Eval; only generic spines and genuinely user-defined quotations fall back to per-element machine execution. This is also why the dispatch recommendations above are deliberately modest: on array workloads dispatch is amortized to noise, and on scalar-loop workloads ecl only needs to be 'scripting fast', not bytecode-VM fast.
GROUNDING: 'A Conversation with Arthur Whitney', ACM Queue 7(2), 2009 (Cantrill interview; the small-interpreter/fat-primitive philosophy); the J incunabulum (Whitney's 1989 one-page J fragment, jsoftware wiki); Lochbaum, BQN implementation notes (mlochbaum.github.io/BQN/implementation/ — simple VM, self-hosted compiler, performance concentrated in primitives); Dyalog idiom recognition as the production mechanism for whole-phrase kernels; ledger decision 21(c) states the same invariant.

## Frame machine shape (the loop the dispatch lives in) [strong]
Keep the explicit reified frame stack — do NOT migrate to host-stack recursion even if tail-call dispatch arrives, because guaranteed TCO, wholesale error unwind, cancellation at safe points, and unit rollback all require frames to be first-class data (this is the defunctionalized-continuation / CEK design: the frame stack is the defunctionalized continuation of a definitional interpreter, per Reynolds and the Danvy school's functional correspondence). But re-shape it: frames become small fixed-size records (view ref, ip, env ref, small kind tag + one or two payload words); combinator state (each/fold indices) lives in the frame, but the skeleton's pattern of moving the entire outer data stack into fat enum variants (EachAfter{outer: Vec<Value>, ...}) must go — with per-unit substacks, a boundary frame records a stack-base index and rollback is truncate-to-base, never clone-and-restore. Inner loop structure: run straight-line through one view with ip in a local, touching the frame stack only at word calls (push), tail calls (replace, giving TCO for free), combinator iterations, and unit boundaries; the error trace is reconstructed by walking the frame stack at unwind time instead of the skeleton's eager per-call trace push/pop.
GROUNDING: Reynolds, 'Definitional Interpreters for Higher-Order Programming Languages' (1972) and Ager/Biernacki/Danvy/Midtgaard, 'A Functional Correspondence between Evaluators and Abstract Machines' (2003) — defunctionalizing the continuation yields exactly this frame machine, and shows TCO = frame reuse; CEK machine literature for boundary frames as control delimiters; CPython's frame objects + generation of tracebacks from frames at raise time (not eagerly) is the production pattern for lazy trace construction; Erlang/BEAM's per-process stacks demonstrate discard-wholesale as the crash-only cleanup primitive.

## Staged plan [strong]
V1 ships: interned symbols; custom list heap object with header (refcount/shared-bit, type/leaf tag, slack capacity, view slot) — required anyway by ledger invariants (a)/(b); lazily-built memoized execution view (constants + interned word ids + span side-table); one switch-dispatch inner loop with uniform handler signatures; small fixed-size frames with stack-base rollback; primitives as core-env bindings with fn-pointer payloads; kernels for pervasive ops and each/fold/scan/where/at/raze over specialized leaves; a global env-generation counter (write-side only — the observability hook, costing one increment per binding write). Stage 2 (only after profiling real workloads): generation-guarded inline caches at CallWord sites; idiom recognition of hot phrases into kernel opcodes at view-build time; static superinstructions for measured pairs. Stage 3 (only if Rust `become` stabilizes AND dispatch appears in profiles, which the K model predicts it will not): mechanical conversion of the switch loop to musttail handler dispatch. Never: dynamic superinstructions via code copying, template JIT, any machine-code emission. The seal layer later reuses this same machinery — a sealed word's 'cached compiled form' is precisely a pre-resolved, guard-free execution view, so nothing built here is throwaway.
GROUNDING: The staging mirrors CPython's actual history (interpreter → PEP 659 adaptive caches → 3.14 tail-call dispatch as a final few-percent option), Brunthaler's measurements that quickening+IC is where interpreter-level gains actually live, and Rohou et al./Nelhage's evidence that dispatch technique is the smallest lever; K/J/CBQN establish that an array language reaches its ceiling through kernels, not dispatch.

## Symbol interning: global append-only intern table, u32 SymbolId, env tables keyed by id [settled-practice]
Intern every symbol/word at read time into one process-global, append-only intern table; a symbol IS a u32 index into that table. Equality and hashing become integer ops; env tables become HashMap<SymbolId, CellRef> (or open-addressed by id); symbol vectors specialize as flat u32 leaves so grade/group/distinct on symbol columns run as integer kernels. The table must be concurrency-safe (sharded lock or lock-free append) because `parse`/`to-symbol` can run inside spawned units — this is the one deliberate shared-mutable carve-out from share-nothing, exactly like Erlang's shared atom table. Accept append-only (symbols never freed) for v1 and document it: `to-symbol` on arbitrary runtime strings can grow the table unboundedly (Erlang's atom table has the same property and a hard limit for that reason); refcounted interning is a later option, not a v1 need.
GROUNDING: kdb+/q: 'symbols are interned strings; comparisons involving them are between their numeric pointers and so are atomic', and q's enumerations reduce symbol columns to integer indexes into the string pool for fast grouping (code.kx.com, timestored.com kdb guides). Erlang: atoms live in one shared VM-global atom table, are never garbage collected, and the table is limited — the canonical precedent and the canonical warning (erlang.org efficiency/atom docs). Lua similarly interns all strings for pointer equality.

## Deep vs shallow binding: keep deep binding (chain search); reject shallow binding/rerooting [strong]
Keep the deep-binding structure: resolution walks the env chain (disposable child -> session -> core; module root -> core). Do NOT adopt shallow binding (one global value cell per symbol, save/restore or reroot on scope entry). Shallow binding is a GIL-shaped design: the per-symbol global cell is shared mutable state that parallel units would race on, and Baker's own model requires rerooting to be an indivisible (i.e. globally serialized) operation for multiprocessing. ecl's chains are structurally short (2-3 links, since quotations capture nothing and module bodies chain straight to core), so deep search is a few probes, and the inline-cache layer (next item) removes even those on the hot path. Shallow binding solves a Lisp-1.5 dynamic-binding problem ecl does not have.
GROUNDING: Baker, 'Shallow Binding in Lisp 1.5', CACM 21(7), 1978 — defines shallow binding via rerooting as an environment-tree transformation and notes multiprocessing correctness depends on rerooting being indivisible; the deep-binding alternative is the ordinary a-list/chain search it optimizes. The multiprocessing serialization cost is exactly why shallow binding died in parallel Lisps and why no modern parallel runtime (Erlang, CPython free-threaded, Rust ecosystems) uses per-symbol global value cells for scoped bindings.

## Late binding + caching: binding cells (rebind-in-place) plus env shape-version guards; cache the cell, never the value [strong]
Represent each binding as a stable heap cell (Arc<BindingCell> whose interior is atomically swappable, e.g. ArcSwap<Binding>). Split writes into two classes: (1) re-def/re-let of an existing name = swap the cell interior — every cached reference to the cell heals automatically, so LATE BINDING costs zero invalidation; (2) creating/deleting a name or changing an env's `uses` list = shape change — bump that env's AtomicU64 shape-version. An inline cache at a word site stores {cell pointer, shape epoch(s) of the envs the miss-path searched}; guard = compare epochs, then load the current word body through the cell. This is precisely CPython 3.12's LOAD_GLOBAL_MODULE design (guard on the dict-keys version, re-read the value through the stored index each execution — assignment to an existing global never invalidates; only key insertion/deletion does) and PyPy's celldict / PEP 280 cells-for-globals. Cache placement: since quotations are immutable plain lists shared across envs, caches cannot live in the list; put them in a per-(body, resolution-env) quickened shadow — an internal threaded array the machine derives and memoizes on first execution, which decision 21(d) explicitly permits ('internal threaded/opcode arrays at most'). Monomorphic caches suffice; PICs are unnecessary because a site under a fixed resolution env has exactly one meaning between shape changes (no receiver-type polymorphism). Route ALL binding writes through one env.bind() function that swaps/inserts, bumps versions, and fires registered watcher callbacks — this is the ledger's required 'binding writes are observable events' and is the hook the seal layer subscribes to; follow CPython's post-PEP-509 direction (PEP 699 repealed the per-dict version tag in 3.13 in favor of targeted dict watchers, PyDict_Watch) rather than resurrecting global version tags as the primary mechanism.
GROUNDING: PEP 659 (Specializing Adaptive Interpreter) and faster-cpython LOAD_GLOBAL specialization: guard on keys version, load by cached index, value re-read every execution. PEP 280 (Guido: 'cells' for globals so rebinding heals references) and PyPy's celldict module-dict strategy (doc.pypy.org). PEP 509 (per-dict version tag) and PEP 699 (its repeal — versions lost to watchers), PyDict_Watch API. Deutsch & Schiffman, 'Efficient Implementation of the Smalltalk-80 System', POPL 1984 (inline caches); Hölzle, Chambers, Ungar, ECOOP 1991 (PICs — surveyed and rejected as unneeded here); Brunthaler, 'Inline Caching Meets Quickening', ECOOP 2010 (inline caches in a bytecode-less/quickened interpreter, the exact shape of the per-body shadow array).

## Module registry: name indirection kept, plus a per-module generation counter as the cache guard [strong]
Keep the skeleton's decision that a binding's `home` is a registry NAME, never an env pointer (hot reload by construction). Make the registry symbol -> ArcSwap<ModuleGen> where ModuleGen { env, generation: u64, name }. Re-registering swaps in a new ModuleGen with generation+1 atomically; a failed module body never swaps (the skeleton's commit-after-success already does this). Qualified-word execution and module-home resolution do one atomic load of the current generation — Erlang semantics: 'fully qualified function calls always refer to current code'. Inline caches of qualified resolutions and the future seal layer's early-bound compiled forms embed the generation they resolved against; guard = one integer compare, and a registry swap invalidates everything derived from the old generation without enumeration. Old generations stay alive as long as in-flight units hold their Arc (Erlang keeps exactly two versions and kills lingerers; Arc-held generations are strictly simpler and safe because they are immutable).
GROUNDING: Erlang/OTP 'Compilation and Code Loading' reference manual: two module versions, current vs old, fully-qualified calls always hit current — the named-indirection hot-reload model the ledger already commits to. The generation-counter-as-guard pattern is the same keys-version/dict-watcher discipline as CPython's global caches (PEP 659, PEP 699) applied at module granularity.

## Lock strategy for parallel units: lock-free snapshot reads (arc-swap discipline), single-writer ownership, no RwLock on the execution path [strong]
Remove every lock from the per-word read path. Ownership rule: an env table is written only by its owning unit (session env by the session thread; a module env only during its own body; disposable children are unit-local, unsynchronized). Anything visible across units — core, registered module envs, the registry — is published via ArcSwap: the table itself is an immutable snapshot; a write clones-and-swaps the table (insert/delete, rare, human-timescale) or swaps a cell interior (rebind, no table clone at all). Readers do a lock-free, mostly wait-free pointer load with no reader-side cache-line contention, unlike RwLock whose read acquisition is itself a contended atomic RMW. Freeze core outright after prelude installation (plain Arc<HashMap>, zero synchronization). Shape versions are AtomicU64. This is the persistent_term bet stated by the ledger's own workload: binding writes happen at typing speed, lookups happen per word execution. Reject per-lookup RwLock (the skeleton), and reject fine-grained locking of chain nodes.
GROUNDING: arc-swap crate documentation (docs.rs/arc-swap): reads always lock-free, mostly wait-free, designed for read-heavy/write-rare shared config — the RCU pattern in Rust. Erlang persistent_term docs: constant-time, no-lock, no-copy reads, deliberately expensive writes, 'suitable for terms frequently accessed but never or infrequently updated' — the same asymmetry. Erlang's per-process heaps justify the single-writer ownership split. Biased reference counting (Choi, Shull, Torrellas, PACT 2018) is the fallback if Arc refcount traffic on cells/values ever shows up in profiles — it exploits the same single-owner skew; u32 symbol ids already remove all RC traffic for the hottest value class in this area.

## Disposable child env per isolated application (each element!): lazy creation on first write [strong]
Never allocate the child env eagerly. Represent the machine's current scope as {local: Option<EnvRef>, parent: EnvRef} (two words, Copy-cheap) or equivalently a needs-child marker on the frame; each/zip-with/for/fold/dict-of/attempt pass the parent env plus the marker. Only when a `def`/`let` actually executes inside the scope does the runtime allocate the child table and swing `local` to it; `defp` legality and module-context discovery still resolve through the parent chain unchanged. Since quotations capture nothing and locals desugar to point-free code before storage (decisions 5, 6), essentially no combinator-applied quotation ever binds — so the per-element cost drops from one Arc+RwLock+HashMap allocation per element (what the skeleton pays at runtime.rs:1548/1585/1641/1398) to copying one pointer, i.e. near-free, while semantics (a temporary def scoped to the element application) are preserved exactly. Note also that on the specialized-leaf fast path decision 21(c) requires kernels to bypass the frame machine entirely, so the child-env question only even arises on the generic-spine fallback; lazy creation makes the fallback cheap too.
GROUNDING: CPython precedent: function frames never materialize a locals dict unless something demands it (fast-locals array; PEP 558/PEP 667 exist precisely because f_locals materialization is the exceptional path) — allocate the mapping only when the semantics are actually exercised. Lua's design similarly allocates upvalue structures only for functions that capture. The general principle — pay for a scope object only on first write — is the environment-side analogue of CoW/uniqueness the ledger already commits to for values.

## Resolution protocol: one lookup per word execution, resolve to a cell once [settled-practice]
The interpreter loop must resolve each word exactly once per execution: resolve to a BindingCell, then use that single resolution for the tail-call/trace decision AND the dispatch (the skeleton resolves twice — once in the tail-detection predicate at runtime.rs:370-374, again inside execute at :610). With the quickened-shadow inline cache, steady-state cost per word is: load cached cell pointer, compare 1-2 shape epochs, load cell interior. Primitives should stop being dispatched by string match on &str (runtime.rs:632-726): give core words cells too (kind=Primitive(fn ptr) alongside Word/Value), so primitive dispatch is the same cell load plus an indirect call — this also lets users shadow primitives uniformly and gives the seal layer one representation to early-bind. Per-token dispatch never needs to be FAST (ledger 21c), but it must not be pathologically slow, and cell dispatch is both simpler and faster than string matching.
GROUNDING: Deutsch & Schiffman POPL 1984 — the entire point of the inline cache is one lookup, then a guarded reuse. Ertl & Gregg ('The Structure and Performance of Efficient Interpreters', and threaded-code lineage from Bell 1973) establish that indirect-threaded dispatch through a resolved cell/fn-pointer is the standard interpreter word-dispatch structure (Forth's code-field-address indirection is literally this design for a late-bound concatenative language: FORGET/redefinition heal via the dictionary entry).

CONFLICTS:
* Share-nothing units vs the intern table: 'units share nothing mutable' cannot be literally true once symbols are interned u32 ids — parse/to-symbol in a spawned unit must write the global intern table. Resolution: one deliberate carve-out, an append-only concurrency-safe intern table (Erlang's shared atom table is the precedent). Also inherits Erlang's known hazard: symbols are never freed, so runtime symbol generation from untrusted strings grows the table unboundedly; document for v1.
* 'Immutable values are shareable across units with no copying' (decision 20) requires atomic (or biased/deferred) reference counting on shared heap values — plain non-atomic refcounts would be unsound the moment a quotation or module env crosses a spawn. This is a values-area cost with an env-area consequence: env cells and module envs must be Arc/atomic, which is fine because their refcount traffic is low; biased RC (Choi et al. PACT 2018) is the escape hatch if profiles disagree.
* Late binding vs inline caching: caching a RESOLVED VALUE or word body at a call site would violate 'redefinition heals callers' (decision 5). No conflict remains only if caches hold binding CELLS and re-read the interior every execution (PyPy celldict / CPython LOAD_GLOBAL_MODULE discipline). The skeleton's ResolvedBinding-cloning pattern, if naively memoized, would freeze bindings — flagged so the real implementation never caches past the cell.
* 'Binding writes are observable events' vs true parallelism: CPython's dict-watcher API is documented as not thread-safe under free-threading (cpython gh-145235). ecl avoids the same trap only because of the single-writer ownership rule — watchers must fire on the owning writer's publish path, and watcher registration itself must go through the same arc-swap discipline. If any future feature lets two units write one env, the observability mechanism has to be redesigned, not just locked.
* Quickened per-(body, env) shadow arrays vs decision 10's 'no bytecode VM unless profiling demands one': the inline-cache carrier I recommend is a derived threaded array, which decision 21(d) explicitly permits ('internal threaded/opcode arrays at most') but decision 10's phrasing discourages building early. Resolution: ship v1 with plain list-walking plus a per-machine (env-epoch-guarded) resolution memo, and keep the quickened-shadow design as the profiled upgrade path; both keep cells+versions as the substrate, so nothing is thrown away.
* Ledger's Binding spec (doc slot, reserved effect slot) is absent from the skeleton — a gap to close, not a design conflict.

## Kernel dispatch structure: op x leaf-tag function table, dispatched once per array [settled-practice]
Give every specialized leaf an O(1)-readable representation tag (I64, F64, Char1, Char2, Char4, GenericSpine, Dict) stored in the value header, and dispatch each kernel through a static (op x left-tag x right-tag) table of monomorphic inner-loop function pointers (unary kernels: op x tag). The table entry is a flat loop over raw slices (e.g. fn(&[i64], &[i64], &mut [i64]) -> Result<(), KernelErr>); missing entries fall through to the generic recursive-descent path. Mixed numeric pairs (i64,f64) get dedicated promote-in-loop entries rather than a materialized cast pass for v1 (a cast-then-dispatch scheme like NumPy's 'safe cast to a defined loop' is the fallback for rare combinations). Dispatch cost is paid once per array operation, never per element — this is exactly decision 21(c)'s 'per-token dispatch never needs to be fast'. The whole kernel surface should be generated from a small macro so each (op, type) loop is monomorphic and autovectorizable, and so a Singeli-style generator can replace the macro later without touching call sites.
GROUNDING: NumPy ufuncs are the canonical production precedent: every ufunc is a static list of 1-D strided inner loops keyed by dtype signature, selected once by type resolution before the loop runs (numpy.org ufunc basics; ufunc.resolve_dtypes). Whitney's J incunabulum (Hui, 'An Implementation of J', Appendix A; jsoftware.com/ioj/iojATW.htm) is the minimal form of the same idea — verb tables indexed by monad/dyad. K per the Whitney/Cantrill ACM Queue interview (2009): 'small, hand-tuned array routines' as the entire speed story. CBQN's dispatch to Singeli-generated per-type kernels is the modern array-language instance (github.com/dzaima/CBQN).

## Pervasion: recursive descent over spines, flat-leaf kernels at the bottom, no materialized broadcasts [settled-practice]
Implement pervasive binary ops as: (1) check the (left,right) tag pair; leaf x leaf of same length -> single kernel loop; leaf x atom / atom x leaf -> scalar-operand kernel variant (the atom is a register value, NEVER a materialized replicated vector); spine x anything -> length-conform check at this level, then recurse per element pair (K leading-axis pairwise descent, decision 3); dict cases keep the skeleton's key-align semantics but on a hash-backed dict. Conformance checking is one length comparison per spine level before descent — there is no separate conformance pass; the first mismatched level raises 'conform with both lengths (matching d.19's expected/got payload). Recursion here is host-stack recursion over DATA depth, which is fine (data nesting is user-bounded, unlike evaluation — keep it out of the frame machine, but add a depth guard converting host-stack exhaustion risk into an ecl error). Overflow-checked i64 loops should use the branchless sign-trick ((a^r)&(b^r)>>63) OR-accumulated into a block flag and checked every block (~1-4K elements), with a scalar rescan on failure to recover the exact element index for the error dict — checked_add per element defeats autovectorization; block-flag accumulation does not.
GROUNDING: K conformability / leading-axis descent is the semantics being implemented (Whitney's K; ledger d.3/d.13). The scalar-operand loop variant instead of materializing a broadcast is universal in NumPy inner loops (stride-0 operands) and CBQN. Block-level error-flag accumulation with slow-path rescan is how CBQN keeps overflow-checked integer arithmetic SIMD-friendly — BQN's fold implementation notes describe performing overflowing + at double width and moving to a full-width accumulator (mlochbaum.github.io/BQN/implementation/primitive/fold.html), and CBQN's arith kernels widen/check per block rather than per element.

## SIMD without JIT: autovectorization first, explicit vectors behind a feature gate, Singeli as the eventual model [strong]
Three layers, all fully compatible with decision 21 (SIMD in precompiled kernels is not JIT). Layer 1 (v1, mandatory): write every inner loop autovectorization-friendly — monomorphic over raw slices, no per-element branches (errors via block flags per the pervasion rec), no per-element allocation, chunked processing with a scalar tail; verify with cargo-asm/llvm-mca style spot checks on the ~10 hottest loops. Layer 2 (when profiling demands): explicit SIMD for the loops autovectorizers miss (compress/where, grade, search, prefix-sum) using stable-Rust mechanisms — safe target-feature std::arch intrinsics (stable since Rust 1.87) or the 'wide' crate; do NOT build v1 on std::simd, which is still nightly-only with no stabilization timeline as of Rust 1.94. Gate Layer 2 behind a cargo feature so the portable scalar build always exists. Layer 3 (post-v1 literature bet): CBQN's Singeli approach — a generator emitting per-type, per-ISA C/Rust kernel variants from one high-level description — is the proven way an interpreted array language gets hand-tuned SIMD across a kernel matrix without JIT; structure the kernel macro so its expansion site is the future generator's insertion point. Runtime ISA multiversioning (compile several variants, select by cpuid at startup) replaces JIT's adaptivity.
GROUNDING: CBQN + Singeli: Singeli is a DSL (implemented in BQN, emitting C) built specifically so CBQN's primitives could use vector instructions while remaining an AOT-compiled interpreter — ~5k lines in production (github.com/mlochbaum/Singeli; github.com/dzaima/CBQN). BQN's replicate/indices notes document SIMD compress strategies (mlochbaum.github.io/BQN/implementation/primitive/replicate.html). Rust SIMD status verified: std::simd nightly-only as of Rust 1.94, safe std::arch intrinsics stable since 1.87 ('The state of SIMD in Rust in 2025', Shnatsel; rust-lang/portable-simd issue #364; pythonspeed.com/articles/simd-stable-rust). Dyalog and K both ship the same architecture: interpreter + AOT vectorized primitives.

## Leaf widths: i64/f64/char{1,2,4} exactly, construction-time specialization, decay-and-promote rules [settled-practice]
Implement exactly the ledger's leaf set: i64, f64, and char leaves width-tagged 1/2/4 bytes per codepoint (PEP 393 model — width is max codepoint width in THIS string, so ASCII is 1 byte/char and indexing is O(1)). Specialize at construction in one pass (the reader and every list-building kernel emit leaves directly when the element type is uniform; cat/cons/raze check tags, not elements). Generalize (leaf -> generic spine of boxed atoms) only on heterogeneous insertion; promote char width on append of a wider codepoint by copying up (amortized into the CoW copy you were doing anyway when shared, or a realloc when unique). Do NOT add i8/i16/i32/bit numeric leaves in v1 — the ledger fixes the atom set and small-int leaves would leak into semantics via overflow behavior — but make the tag enum and dispatch table extensible because the K-order ceiling will eventually want them (see conflicts). Mixed int/float lists stay generic spines in v1; do not auto-promote (decision 4 bans promotion divergence).
GROUNDING: PEP 393 (CPython flexible string representation) is the named model in the ledger and in production since Python 3.3: per-string width tag 1/2/4, O(1) indexing, ASCII compaction. CBQN uses per-array element widths (i8/i16/i32/f64, c8/c16/c32) chosen at construction and widened on demand — its implementation notes and bencharray treat width as the dominant performance variable (mlochbaum.github.io/BQN/implementation/). K similarly specializes homogeneous vectors at construction. Construction-time specialization with O(1) tag query is what makes the op x tag dispatch table possible at all.

## Idiom / fast-path recognition under late binding: structural match + resolution guard at combinator entry, snapshot semantics [strong]
Recognize patterns at ISOLATED-combinator entry (fold/scan/each/zip-with), once per array operation: structurally match the quotation against a small closed pattern table — (w) where w is a single word, for fold/scan/each — then GUARD by resolving each word in the quotation against the application env and checking pointer-identity with the core primitive's binding. Guard passes -> run the fused kernel (sum, product, min/max, prefix-sum, pervasive-op-one-level-down for each); guard fails (user re-defined +) -> generic per-element path, which is always semantically complete. This is sound under late binding precisely because the check happens at every application, after resolution, and costs O(quotation length) against an O(n) loop — no caching, no invalidation needed for v1. Dyalog-style raw token-pattern recognition WITHOUT the resolution guard is unsound in ecl (Dyalog idioms are safe only because APL primitives are not redefinable). Two soundness details to pin in the ledger: (a) specify that an isolated combinator resolves its quotation's words once at entry (snapshot semantics) — this is needed anyway if envs are shared across truly parallel units, else guard-then-run has a TOCTOU race, and it makes fusion correct by definition; for single-word quotations like (+) it is unobservable in a single unit since the body cannot re-def mid-loop; (b) fused kernels skip decision 14's per-element contract check — sound because the recognized primitive satisfies ( a -- b )/( acc a -- acc ) by construction. Larger fusions ('where at' filter, 'dup grade at' sort) should be recognized inside PRELUDE word bodies at def-time of the prelude only, or as multi-token patterns at call boundaries, with the same resolution guards. If per-call guard cost ever shows up in profiles, add binding-generation counters invalidated through the ledger's 'binding writes are observable events' — the CPython lesson is to prefer targeted watcher/event invalidation over global version tags (PEP 509's dict version tag ended up unused by the specializing interpreter and was removed by PEP 699).
GROUNDING: Dyalog idiom recognition: documented idiom list where specific token phrases (',/', '{omega[grade omega]}' sort, first-reverse) are special-cased into better algorithms (help.dyalog.com 17.0 Idiom List; Dyalog APL Idioms cheat sheet) — precedent for the pattern table, with the caveat that APL primitives are fixed symbols. BQN fast paths: fold.md notes that + and x on integers may be reordered for SIMD because exact, and CBQN dispatches folds of known primitive functions to dedicated kernels (mlochbaum.github.io/BQN/implementation/primitive/fold.html). Whitney's K special-cases composite verb phrases the same way. Guard/invalidate precedent: CPython PEP 659 specializing adaptive interpreter (guarded specialized instructions, deoptimize on guard failure) and PEP 509 -> PEP 699 history showing version-tag guards superseded by watcher-based invalidation (peps.python.org/pep-0659, pep-0509, pep-0699).

## Sorting and grading: range-adaptive counting/radix on leaves, stable comparison fallback on spines [strong]
grade on an i64 leaf: one min/max pass first; if range is small (<= max(n, ~64K)) use counting sort on keys carrying u32 index payloads; else LSD radix on the key bytes (skip constant high bytes detected by the min/max pass) with index payload; below ~100-200 elements use insertion/comparison sort directly (radix constants lose on short arrays). f64 leaf: order-preserving bit flip (x ^ (x>>63 | sign fixup)) then the same u64 radix — ecl's guarantee that NaN never exists (d.22) removes the only complication in float radix sorting. Char leaves: counting sort at width 1, counting/radix at 2 and 4. Generic spines: stable comparison sort (Rust's stable driftsort) over structural compare — grade MUST be stable at every path (K/APL grade stability is relied on by group/distinct idioms). sort: prelude says 'dup grade at', but recognize the idiom (per the recognition rec) and call a direct value sort on leaves — sorting values directly avoids the gather and is meaningfully faster; on spines fall back to the literal grade+at. distinct/group: hash-based on leaves (open-addressing with i64 keys), never the skeleton's O(n^2) scan; on small-range ints use a direct-addressed table (counting-sort-style).
GROUNDING: BQN's sorting implementation notes (mlochbaum.github.io/BQN/implementation/primitive/sort.html): LSD radix ~3x faster than fluxsort on random 4-byte data; counting sort dominant for small ranges/1-byte; radix's constant overhead makes it useful only above ~100 elements; CBQN ships counting+radix for 1-4 byte elements with generic Timsort for 8-byte — ecl should push radix to 8-byte keys since i64 is its only int width, using the min/max prepass to shrink effective key width (the same width-reduction CBQN gets from its small-int types). Dyalog recognizes the sort idiom '{omega[grade omega]}' to run a direct sort instead of grade+index (Dyalog Idiom List). Float bit-flip radix is standard (used in CBQN and GPU sorting literature).

## The prelude question: no dual representation in v1 — kernel speed flows through combinator-entry recognition; the sealed cached form comes later [strong]
Prelude words stay honest ecl source and 'body' returns the real stored list, with NO shadow representation in v1. sum = (0 (+) fold) gets kernel speed automatically: executing sum runs fold, and fold's entry-point recognition (structural match + resolution guard, above) selects the sum kernel. The stored list is the only semantic truth; the kernel is an unobservable fast path chosen after guards pass — the exact doctrine the ledger already uses for CoW ('performance model, not semantics'). This means prelude speed requires zero new mechanism and survives any user re-def of + or fold (guards fail, generic path runs, semantics preserved). The dual representation ('compiled form cached on the binding, guarded') is real but belongs to the seal layer the ledger already reserves: a sealed word early-binds callees and caches an internal opcode/threaded array (decision 9, d.21(d)) — at which point the guard becomes 'sealed dependencies cannot be re-defed' rather than a per-call check, and the binding's reserved effect/cache slots hold it. Design the binding struct now with the cache slot present-but-unused (the ledger already reserves it), and route every binding write through the observable-event hook so seal-time invalidation works without refactoring.
GROUNDING: This mirrors how CBQN handles derived expressions: recognition happens where the combinator (modifier) is applied — fold of known primitive + dispatches to a sum kernel without the user-visible function changing identity (BQN fold.md implementation notes). Dyalog likewise recognizes phrases at execution sites, not by rewriting stored definitions (Dyalog Idiom Recognition docs). The guarded-cache endgame is CPython PEP 659's model (specialized form + guards + deopt), and the invalidation-hook requirement matches the PEP 509->699 lesson that binding-write events must be first-class from the start.

## Value memory layout prerequisites the kernels depend on (uniqueness + slack capacity) [settled-practice]
Kernels must be able to (a) ask 'is this leaf uniquely held?' in O(1) and steal its buffer as the output (in-place +, filter, etc. when refcount==1), and (b) append into slack capacity — so leaves need a header carrying {tag, length, capacity, refcount} with bucket-sized (power-of-two or size-class) allocation. Use plain non-atomic refcounts within a unit ONLY if values never cross units without a handoff protocol; since the ledger mandates zero-copy sharing across truly parallel units, use atomic refcounts on leaf headers but load them with Relaxed for the uniqueness test (Swift's isKnownUniquelyReferenced model) — uniqueness-based reuse remains correct because refcount==1 observed by the only holder is stable. Every kernel should take ownership of its inputs and apply the reuse rule uniformly (output buffer := left input if unique and same width, else right input if unique, else fresh) — this single rule is where 'hidden in-place mutation' lives and it must be in the kernel calling convention, not ad hoc per kernel.
GROUNDING: Whitney, ACM Queue 2009 interview: K is refcounted with no GC, and 'if you're doing a vector operation and the reference count is one, then reuse the vector' — the exact rule, stated by the primary source. Perceus (Reinking, Xie, de Moura, Leijen, PLDI 2021, distinguished paper) formalizes precise-RC reuse analysis and guaranteed in-place updates ('functional but in-place') — the theory backing the uniform ownership-passing kernel convention. Swift CoW arrays ship isKnownUniquelyReferenced-guarded mutation in production. CBQN and K both use bucket/size-class allocators so slack capacity exists to append into.

CONFLICTS:
* Float fold reassociation vs SIMD: the ledger defines fold as a strict left fold and the prelude defines sum = (0 (+) fold), so a SIMD sum kernel (multiple accumulators or pairwise) observably changes f64 results and can change WHERE d.22's 'overflow (non-finite from finite) fires. BQN explicitly reorders only integer +/x folds because they are exact. The ledger needs a ruling: either (a) float folds stay strictly sequential (integer/min/max folds vectorize freely — recommended, honest, costs float-sum throughput), or (b) the ledger blesses a documented deterministic reassociation (pairwise/blocked, NumPy-style) as the semantics of the recognized sum kernel. Silent divergence between the fused and generic paths is not an option — guard failure would change numeric results, which breaks the recognition-is-unobservable doctrine.
* Closed atom set (int64-only integers) vs the K-order ceiling: comparison kernels must produce 0/1 int64 mask leaves, an 8x memory-traffic penalty over CBQN's i8/bit booleans, and where/filter/group on masks become memory-bound at 1/8 the achievable rate. Same for small-range data (bytes, flags). No v1 action needed, but decision 21's 'K-order performance is the ceiling the architecture can evolve to' likely eventually requires narrow/bit leaf REPRESENTATIONS (semantically still int64 atoms, same doctrine as CoW); the leaf-tag enum and dispatch table must be built extensible now or this becomes a rewrite.
* Integer-overflow-as-error (d.4) and error-dicts-name-the-element (d.19) vs autovectorization: per-element checked arithmetic defeats SIMD. Resolution (block-level error-flag accumulation, then a scalar rescan to identify the exact failing element only on the error path) is sound because the kernel's partial output is discarded wholesale (crash-only), but it means error DETECTION is batched — fine under the ledger only because no partial result is ever observable. Worth stating in the ledger so nobody 'fixes' the batched check later.
* Late binding (redefinition heals callers) vs any cached fast path: per-call resolution guards at combinator entry are sound but assume word resolution is atomic across the guarded kernel run. If environments are shared mutably across truly parallel units (the ledger's no-GIL requirement plus 'env writes survive'), a concurrent re-def of + mid-kernel creates a guard TOCTOU window. Recommended ledger addition: isolated combinator application resolves its quotation's words once at entry (snapshot semantics). Without this ruling, fusion soundness rests on an unstated memory-model assumption.
* Fused kernels vs d.14's per-application dynamic contract checks: the fused path never runs the quotation, so 'violation = immediate error naming the element' can never fire on it. This is benign (recognized primitives satisfy the contract by construction) but is a formal behavioral difference the ledger's contract language should acknowledge.
* d.16 printing exposes representation + construction-time specialization means kernel OUTPUT representation is user-visible: a fused filter that produces a flat leaf where the generic per-element path would produce the same leaf is fine, but every kernel must normalize its output exactly as construction would (e.g. an each fast path returning an f64 leaf while the generic path builds a spine that then specializes identically) — representation parity between fused and generic paths is a testable invariant the implementation must enforce, or recognition becomes observable through the prompt's brackets.

===== AREA: scheduler =====

## Unit representation: unit = movable heap-allocated frame machine (stackless green process), never one OS thread per unit [strong]
Represent a unit as a plain heap struct: (frame vec, data stack vec, env ref, control block). Decision 10 (no evaluation recursion on the host stack, ever) means a unit's complete execution state is already explicit data — suspension is 'stop stepping', resumption is 'resume stepping', and migrating a unit between OS threads is moving a struct. This makes spawn cost a small allocation (hundreds of bytes), which is mandatory because par-each is stdlib over spawn and may spawn one unit per element. Reject thread-per-unit: OS thread creation (microseconds, megabyte stacks) cannot support per-element spawn granularity. The frame machine and the scheduler are the same design decision; this synergy is the single most important architectural fact in this area.
GROUNDING: BEAM processes: each Erlang process is a small heap-allocated PCB multiplexed onto one scheduler thread per core, preempted between dispatch steps (theBeamBook, scheduling chapter; Hamidreza Soleimani, 'Erlang Scheduler Details'). Cilk-5's work-first principle (Frigo, Leiserson, Randall, PLDI 1998) demonstrated spawn cost can be 2–6x a function call when spawn-side overhead is minimized — the requirement par-each imposes. Stackless suspension is exactly a defunctionalized CEK-style continuation (Reynolds definitional interpreters): the frame stack IS the reified continuation, so 'park unit, resume later' needs no mechanism beyond what decision 10 already mandates.

## Threading model: fixed pool of N≈cores worker threads, per-worker run queues + work stealing; global injector queue [strong]
Run a fixed pool of worker OS threads (default = logical cores; 1 worker must remain a supported degenerate config for debugging). Each worker owns a local run queue of ready units; spawns from a running unit push locally; a shared injector queue takes spawns from the REPL thread and timer thread; idle workers steal. For v1 a single mutex-protected global run queue is acceptable at scripting scale — the invariant to protect is 'unit is a movable object', not the stealing policy. When contention matters, adopt Tokio's refinements over naive Chase-Lev: fixed-size local ring buffer, steal-half into the local queue, overflow to the global queue, throttled concurrent stealers. Use crossbeam-deque or hand-rolled ring per Tokio's design; do not build a priority scheduler — units are CPU-fair via fuel (see safe points).
GROUNDING: Tokio's work-stealing scheduler rewrite ('Making the Tokio scheduler 10x faster', Tokio blog 2019; tokio-rs/tokio PR #1657) documents moving from crossbeam's Chase-Lev deque to a fixed ring + steal-half + stealer throttling, with measured 10x improvement. Chase & Lev's dynamic circular work-stealing deque (SPAA 2005) is the base structure crossbeam implements. BEAM runs one scheduler thread per core with per-scheduler run queues plus task migration/stealing (theBeamBook scheduling chapter; AppSignal 'Deep Diving Into the Erlang Scheduler'). Cilk-5 (PLDI 1998) is the provably-efficient work-stealing ancestor.

## Safe-point mechanism: fuel/reduction counting in the dispatch loop; chunked fuel checks inside kernels; no signals ever [settled-practice]
Give each unit a fuel counter decremented once per frame-machine dispatch step; at zero (every ~2k–4k steps), hit a safe point: check the unit's atomic cancel flag, check preemption (reschedule if other units are runnable), reset fuel. This is BEAM reduction counting transplanted directly — an interpreter dispatch loop is a natural safe point on every iteration, so ecl never needs Go-style signal-based preemption (Go was forced to signals in 1.14 only because compiled tight loops have no dispatch points to instrument). The one gap is ecl's own 'NIF problem': coarse kernels (decision 21c) run a single loop over a flat leaf as ONE frame step, so a kernel over a 10^9-element leaf would be uncancellable for seconds. Kernels must decrement fuel per chunk (e.g. every 64K elements — cost is unmeasurable against the loop body) or, for genuinely unbounded work (IO), be routed to the blocking pool. Cancellation observation is purely cooperative and only at these safe points; acting on cancel = discard the unit's frames and substack wholesale, which is free because units share nothing mutable.
GROUNDING: BEAM: per-process reduction counter, preemption when the slice (~2000 reductions historically, CONTEXT_REDS=4000 in modern ERTS) is exhausted; long-running native code (NIFs) broke this model and forced dirty schedulers in OTP 17+ — the direct precedent for why ecl kernels need intra-kernel checks (theBeamBook scheduling chapter; erl_nif docs on dirty NIFs; Soleimani 'Erlang Scheduler Details'). Contrast: Go proposal 24543 ('Non-cooperative goroutine preemption') documents that cooperative prologue checks caused unacceptable tight-loop slowdowns in compiled code, motivating Go 1.14's signal-based async preemption — the failure mode an interpreter structurally avoids.

## Cancellation propagation and the scope tree: intrusive ownership tree, single-writer children lists, cancel-flag + recursive descent, wait-for-quiescence at scope close [strong]
Each unit's control block carries: parent task handle, a children vec of task handles it spawned, and per-task an atomic cancel flag. The children list needs no lock: only the owning unit appends (at spawn) and walks it (at its own death/scope-end), on its own thread. cancel(task) = set the flag, then recursively flag descendants (each task cell stores its own children snapshot or the cancelling thread walks via the child unit's control block under a small per-task mutex — flags only, never execution state). Cancellation lands only at the target's safe points. At scope end (unit completes or dies): walk children, cancel unawaited ones, then WAIT for all children to reach terminated state before the unit itself reports its outcome — Trio semantics. Without quiescence, cancelled grandchildren's in-flight IO outlives the scope and 'a failed unit leaves nothing' silently weakens. The REPL session is the root scope node; `tasks` is a walk of the live tree.
GROUNDING: Nathaniel J. Smith, 'Notes on structured concurrency, or: Go statement considered harmful' (vorpus.org, 2018): the nursery tree, cancel scopes, and the rule that a nursery never lets a task escape supervision, waiting for full cleanup even mid-cancellation. Java's StructuredTaskScope (JEP 453/505/525, Project Loom): explicit ownership hierarchy — forks owned by scope, scope owned by creating thread, shutdown interrupts all active forks, cancellation propagates both down and up the nested-scope tree; join waits for all subtasks. BEAM's exit-signal linking is the older precedent for death-propagates-to-related-processes, but the Trio/Loom tree (not BEAM's symmetric links) matches ecl's parent-owns-children spec.

## Task cells and parking: write-once multi-waiter cell; await suspends the unit, never blocks the worker thread [strong]
Task cell = { state: Pending(Vec<UnitHandle>) | Done(outcome Value) | (Cancelled folds into Done with the 'cancelled error dict), cancel_flag: AtomicBool } under a small per-cell mutex (upgrade to an atomic state machine only if profiling demands). await is a frame operation: push an Await frame, lock the cell — if Done, push cached outcome and continue (idempotence = read the cached value; handles are dup-able values, so MULTI-waiter support is mandatory, unlike Tokio's oneshot); if Pending, append this unit's handle to the waiter list and detach the unit from the worker (parked). Completion transitions to Done exactly once and moves all waiters to run queues. This design eliminates the classic finite-pool deadlock (all N workers blocked in await on units queued behind them) that blocking-thread await would create. await-any: register in every cell plus a shared CAS'd once-flag; first completer wins, delivers (index, outcome); unregister from the rest lazily (stale waiters check the once-flag on wake). await-for: register both in the cell and in a timer facility — v1: one timer thread + binary heap; scale-up: hierarchical timing wheel. attempt stays the in-machine synchronous frame operation (spawn-await equivalence is observational, not implementation): never route REPL error handling through the scheduler.
GROUNDING: The parked-continuation design is BEAM's receive-blocking (process descheduled, moved to waiting, re-enqueued on message arrival — theBeamBook scheduling chapter: process states runnable/waiting/running) and every async runtime's waker protocol (Tokio task parking/notification). Write-once multi-reader outcome is a promise/IVar; deterministic-by-join-order gathering matches StructuredTaskScope.join semantics (JEP 453/505). Timing wheels: Varghese & Lauck, 'Hashed and Hierarchical Timing Wheels' (SOSP 1987) — O(1) start/stop/expire; production adopters Netty HashedWheelTimer and Kafka's hierarchical wheel; a binary-heap timer is standard and sufficient at scripting scale.

IMPLEMENTATION FOLLOW-UP (2026-08-14): Negele, Friedrich, Oh, and Egger, "On the Design and Implementation of an Efficient Lock-Free Scheduler" (2015), separates two concerns that the first wait-set draft conflated. Its task-switch finalizer closes the check/enqueue/sleep lost-wakeup window by rechecking only after the suspended task is safely published; this supports ecl's registering/selected/active wait phases. Its safe node reuse is a different protocol based on processor-local hazard pointers and an `uncooperative` region that bounds concurrent access by the processor count. Ecl cannot inherit that reclamation proof because Units migrate and the shell exposes no processor-pinned uncooperative region. Cross-thread wake registrations therefore use stable owning handles, following Rust's `Waker`/`Arc` contract, and the pure core models directory cleanup and detached-delivery return in either order. Aggarwal and Sarangi, "Lock-free and Wait-free Slot Scheduling Algorithms" (2015), addresses linearizable reservation of contiguous time/resource slots with CAS, request descriptors, and helping; it is not a runnable-task scheduler. Its applicable lesson is methodological—explicit states, declared linearization points, and separate lock-free versus wait-free progress claims—not an algorithm to import into ecl's run queue.

## Refcount atomicity and cross-unit value flow: share everything (no copy-on-send), v1 = atomic RC uniformly, biased RC as the measured upgrade; reject the BEAM copy-small hybrid [strong]
Keep the ledger's share-everything commitment: values cross unit boundaries by reference, so ALL refcounts must be thread-safe from day one — v1 should use plain atomic RC (Rust Arc) with the standard uniqueness protocol: 'uniquely held?' = strong count == 1 read with Acquire ordering (synchronizing with Release decrements from concurrent drops), which is exactly Arc::get_mut/make_mut and Swift isKnownUniquelyReferenced semantics — CoW+uniqueness (decision 1) remains sound under parallelism with this discipline and no other change. Analysis of the BEAM hybrid, as asked: BEAM copies messages because per-process heaps exist to let each process GC independently under a TRACING collector; ecl has eager RC, not tracing GC, so per-unit heaps purchase nothing, and copy-on-send would violate decision 20's explicit 'no copying or serialization' text. BEAM's refc binaries are the half of the hybrid ecl should generalize: >64-byte binaries live on a shared heap, are reference-counted, and are NOT copied on send — production proof that shared refcounted immutable buffers across truly parallel schedulers work; ecl's flat leaves are precisely this, extended to all values (and BEAM's refc-binary leak pathology stems from tracing-GC delay of ProcBin release, which eager RC does not have). Upgrade paths if atomic RC shows up in profiles (it is per-value, not per-element, so the coarse-kernel model amortizes it — measure before optimizing): (a) biased RC — owner thread non-atomic fast path, foreign threads atomic on a second field (Choi, Shull, Torrellas 2018; shipped in free-threaded CPython per PEP 703, officially supported in 3.14 with PEP 779) — but note it complicates the uniqueness query (must consult two counters + ownership), so adopt only with a worked CoW protocol; (b) Lean/Koka-style mark-on-share — non-atomic RC by default, values reachable from a spawned quotation get marked multi-threaded (then atomic forever) at spawn time; marking cost is proportional to spine node count, small for ecl's flat-leaf-heavy data, but it is a v2 optimization. Coordinate with the values area: the sharing-metadata slot must be sized/aligned for whichever scheme wins.
GROUNDING: Erlang efficiency guide ('Constructing and Matching Binaries', erlang.org): heap binaries ≤64 bytes copied on send; refc binaries on a shared heap with a reference counter, sent by reference — the closest production precedent for cross-process shared immutable buffers. Choi, Shull & Torrellas, 'Biased Reference Counting: Minimizing Atomic Operations in Garbage Collection' (2018), adopted by PEP 703 / free-threaded CPython (officially supported per PEP 779, Python 3.14, Oct 2025; Victor Stinner, 'Free Threading internals: reference counting') alongside deferred RC — the production template for cheap thread-safe RC without a GIL. Ullrich & de Moura, 'Counting Immutable Beans' (IFL 2019, Lean) and Reinking, Xie & Leijen, 'Perceus: Garbage Free Reference Counting with Reuse' (PLDI 2021, Koka): precise RC on immutable data with reuse; Lean's runtime marks objects shared across threads to gate atomic ops. Swift isKnownUniquelyReferenced (Swift ARC optimization docs; Swift forums CoW threads) and Rust Arc::get_mut ordering discussion (rust-lang/rust #24880, std Arc docs: Acquire on the counts synchronizing concurrent drops) establish the sound uniqueness-under-atomics protocol.

## IO ordering within a unit; blocking IO on worker threads [strong]
Intra-unit IO ordering is free: a unit executes its frame machine sequentially, so IO effects occur in program order with no extra mechanism — the only guarantee to add is per-call atomicity of console writes (take the stdout lock for the duration of one print/prin call) so concurrent units interleave at whole-write granularity, never mid-line; this satisfies decision 11/20 exactly ('within a task IO is ordered; across tasks, unspecified'). Blocking IO: v1 may execute IO words directly on the worker thread — at scripting scale, stalling one of N cores during a file read is acceptable and simple. The committed evolution path reuses the await mechanism unchanged: an IO word packages the syscall as an internal completion cell, hands it to a separate elastic blocking pool, and parks the unit on the cell — identical to await, no new machinery — mirroring Tokio's core-pool/spawn_blocking split (blocking pool grows on demand to a cap, default 512 threads) and BEAM's dirty IO scheduler set (introduced with dirty schedulers OTP 17+, default 10 dirty IO schedulers) which exists precisely because long IO on a normal scheduler thread starves the reduction-counted world. Timers never live on workers: the timer thread owns deadlines and completes 'timeout' outcomes through the same cells.
GROUNDING: Tokio runtime Builder / task::spawn_blocking docs: dedicated dynamically-grown blocking pool (cap 512 by default) so blocking work never occupies core worker threads. Erlang erl_nif documentation and OTP dirty-scheduler history (erlang/otp commit c1c03ae, OTP 17): work that cannot complete in ~a millisecond must move to dirty CPU/IO schedulers rather than stall a managed scheduler. BEAM's io-server (group leader) process serializes console output per node — the precedent for whole-write atomicity to shared streams.

## Determinism guarantees vs the scheduler: determinism lives at join points, not in scheduling [strong]
Do not attempt deterministic scheduling. The ledger's determinism guarantees (await order is program order; par-each's leftmost-error) are join-order properties: par-each spawns all units, then awaits handles in index order and re-raises the first 'err — the result is identical under any work-stealing schedule. Preserve this framing as an explicit invariant so no future contributor 'fixes' apparent nondeterminism by constraining the scheduler (which would destroy parallelism). The two sanctioned nondeterminism points — await-any's winner and cross-unit IO interleaving — are the ONLY scheduler-visible behaviors; everything else must be schedule-invariant, which is testable: run the suite with 1 worker and N workers and with a randomized-steal stress mode, asserting identical outcomes (BEAM's approach of testing with different scheduler counts; Loom-style schedule exploration is overkill here because units share nothing).
GROUNDING: StructuredTaskScope (JEP 453/505): results gathered by join in fork order regardless of completion order — the same deterministic-join pattern. Trio ('Notes on structured concurrency'): nursery exit as the single synchronization point making concurrent code composable. The share-nothing precondition that makes schedule-invariance actually hold is BEAM's process isolation model (theBeamBook): no shared mutable state means scheduling cannot be observed except through declared channels.

SKELETON VERDICTS:
* Nothing in the skeleton implements concurrency at all — spawn/await/await-any/cancel/par-each exist only in design/VOCABULARY.md (lines 166–172); the scheduler is greenfield, so the verdicts below are about structures that block or enable it.
* MUST NOT SURVIVE: Machine borrows &mut Runtime and the data stack lives on Runtime (poc/rust/src/runtime.rs:309–313, stack field on Runtime; Machine::new takes &'runtime mut Runtime) — exactly inverted for share-nothing units. The real implementation needs unit-owns-(frames, data stack, env ref) with Runtime/session reduced to shared services (module registry, scheduler handle, IO); a unit must be a self-contained Send struct.
* MUST NOT SURVIVE AS-IS: EnvRef = Arc<RwLock<Environment>> (poc/rust/src/runtime.rs:10) with a read-lock taken on every word lookup. Under N parallel units this puts a contended lock on the hottest path in the interpreter — a GIL-shaped design by the ledger's own definition — and RwLock writes are not the 'observable binding events' the seal layer requires. Needs a concurrent env design (epoch/snapshot reads or lock-free read path) coordinated with the environments area.
* SHOULD SURVIVE, GENERALIZED: attempt's substack isolation — std::mem::take of the outer stack + Frame::AttemptAfter{outer, trace_depth} + catch_attempt unwinding (poc/rust/src/runtime.rs:1860–1869, 329, 729) — is precisely the unit-rollback/outcome-reification machinery spawn needs. Promote it from a special frame into the unit boundary itself: spawn = run that same isolated substack on another worker; attempt = the synchronous in-machine case (do NOT literally implement attempt as spawn+await through the scheduler).
* SHOULD SURVIVE: the explicit Frame enum with defunctionalized combinator continuations and zero host-stack recursion (poc/rust/src/runtime.rs:243–307, run loop at 324–339). All frames already hold Arc'd code and env refs, so a unit is accidentally close to a movable heap object already — the frame-machine architecture is the enabler of the whole green-unit scheduler and must be preserved through the rewrite.
* SURVIVES BY LUCK, VERIFY DELIBERATELY: Value is built entirely on Arc (poc/rust/src/value.rs — Arc<str>, Arc<[Value]>, Arc<[(Value,Value)]>), so the skeleton is already atomic-RC and structurally Send/Sync-capable. The real implementation should keep atomic RC but add a static assertion (Value: Send + Sync) and design the sharing-metadata word (refcount/shared bit for CoW uniqueness) knowing it must be thread-safe — the skeleton has no uniqueness detection or slack-capacity mutation at all, and generic Arc<[Value]> spines with no flat leaves violate invariant 21(a) (values area's problem, but the atomicity decision is shared with this area).
* MISSING, MUST BE ADDED: the dispatch loop (run(), poc/rust/src/runtime.rs:324–339) has no fuel counter, no safe-point check, and no yield mechanism; kernels do not exist yet (each/fold run per-element through frames) so there is no chunked-cancellation story to inherit — build fuel accounting into the very first version of the real dispatch loop, since retrofitting safe points is what forced Go into signal-based preemption.

CONFLICTS:
* Ledger decision 20 ('Immutability makes sharing safe with no copying or serialization') forecloses the BEAM copy-small/share-large hybrid the task asked to analyze: message copying, even for small values, would contradict the ledger's text. Recommended resolution: keep share-everything (BEAM's copying exists to serve per-process tracing GC, which ecl doesn't have), and accept the honest cost — every value's refcount is thread-safe, an overhead K itself never pays (K is single-threaded with non-atomic RC). This is a real tension between decision 20 and decision 21's 'K-order performance ceiling': the ceiling must be restated as 'K-order minus atomic-RC overhead' unless biased RC or mark-on-share closes the gap later.
* Ledger Scheduler section says 'Cancellation lands at frame boundaries' while decision 21(c) requires coarse kernels to execute as SINGLE runtime loops over leaves. A pervasive-multiply over a 10^9-element leaf is one frame step, so strict frame-boundary cancellation gives unbounded cancellation latency — the same collision BEAM hit with long-running NIFs, which forced dirty schedulers. Resolution: read 'safe points' as including chunk boundaries inside kernels (fuel decrement every ~64K elements); this preserves both invariants and should be written back into the ledger.
* Decision 20's '`attempt` ≡ `spawn await`' read as an implementation directive would route every REPL error boundary through the scheduler (allocation, cell, possible cross-thread hop) — in tension with decision 21's cold-start soul test. Resolution: the equivalence is observational; attempt stays the in-machine frame operation the skeleton already proves, sharing the isolation code path with spawn.
* Structured-lifetime under-specification: 'dropped handles are cancelled at scope end' does not say whether scope close WAITS for cancelled children to terminate. Without wait-for-quiescence, a cancelled child's in-flight IO can outlive its scope, quietly weakening 'a failed unit leaves nothing' beyond the ledger's stated stack-only carve-out. Trio and Java's StructuredTaskScope both wait; recommend ecl adopt waiting and record it in the ledger.
* Cross-area dependency (values area): CoW uniqueness detection ('uniquely held?') must be defined against atomic refcounts with Acquire/Release discipline from day one (Arc::get_mut / isKnownUniquelyReferenced semantics). If the values area later adopts biased RC (PEP 703-style) or Lean-style mark-on-share for speed, the uniqueness query changes shape (two counters + ownership, or shared-bit consultation) — the two areas must move together; neither may assume a plain non-atomic count.
* Cross-area dependency (environments area): the skeleton's Arc<RwLock<Environment>> per-lookup locking is the one place a GIL could sneak back in. Late binding means env reads happen on every word execution in every parallel unit; the env's concurrent-read design is scheduler-critical, not just an environments-area concern.

===== AREA: frames =====

## Machine shape: keep the explicit frame machine, understand it as a defunctionalized CEK machine with a flat continuation stack [settled-practice]
Keep the skeleton's fundamental shape — an explicit loop over (Control=code+ip, Environment=EnvRef, Kontinuation=frame stack) with no host-stack recursion — and make the continuation a flat, contiguous array of frames (it already is a Vec; keep that, never a linked heap structure). Each combinator variant in the Frame enum is exactly a defunctionalized continuation constructor; this is the correct, literature-blessed design for guaranteed TCO, wholesale unwinding, and iterative recursion combinators. What the literature says about making such machines fast: (a) the continuation must be a stack, not heap-linked closures; (b) the machine registers (code pointer, ip, data-stack top index, env) must live in host locals inside the dispatch loop, spilled to the frame only at genuine suspension points (calls, combinator iterations); (c) dispatch happens on the token stream, and frame-kind dispatch happens only at returns, which are far rarer than tokens.
GROUNDING: Reynolds, 'Definitional Interpreters for Higher-Order Programming Languages' (1972) originated defunctionalizing an interpreter's continuations into first-order data; Ager, Biernacki, Danvy & Midtgaard, 'A Functional Correspondence between Evaluators and Abstract Machines' (PPDP 2003, BRICS RS-03-13) proves the CEK machine is mechanically the CPS+defunctionalized evaluator — the frame variants ARE the defunctionalized continuation constructors, so the skeleton's design is principled, not ad hoc. Ertl & Gregg, 'The Structure and Performance of Efficient Interpreters' (JILP 2003) establishes that efficient interpreters keep VM registers (ip, sp) in host registers/locals and that dispatch structure dominates interpreter cost; their measurements (threaded code ~2x over switch, BTB misprediction rates 81–98% for switch) also justify NOT chasing dispatch speed here, since ecl's ledger amortizes dispatch over fat kernels (K/J model; Whitney's one-page J incunabulum demonstrates the tiny-interpreter-over-array-primitives architecture).

## Frame representation: small uniform frames indexing into per-unit stacks; abolish fat variants that own moved-out stacks [strong]
Replace the skeleton's large enum variants (ZipWithAfter is ~120+ bytes and several variants own a whole `outer: Vec<Value>` moved out of the data stack) with small (target ≤48-byte) uniform frame records that hold: a code reference (Arc/id), an ip, an env ref, and small aux fields (item index; a base index into the data stack; a base index into a per-unit results area). The key change: substack isolation for attempt/dict-of/each/module bodies is a BASE POINTER (stack mark) into one contiguous per-unit data stack plus an underflow barrier — never `std::mem::take` of the stack into the frame. 'Discard substack + frames wholesale' then becomes: truncate data stack to the boundary's saved base, truncate frame stack to the boundary's index — O(1) bookkeeping plus the unavoidable drops. Combinator working state (each's accumulating results) should live in a region of the unit's data stack above a recorded base (or a per-unit scratch stack), not in per-frame Vecs, so frames stay POD-small and copy-free on push/pop. Spawned units get their own stacks entirely (share-nothing), so a dying unit frees wholesale like a BEAM process heap.
GROUNDING: Forth's canonical two-stack architecture and Factor (Pestov, Ehrenberg & Groff, 'Factor: a dynamic stack-based programming language', DLS 2010) both run concatenative code with separate contiguous data/retain/call stacks addressed by pointers, with quotation calls marking depths rather than copying stacks; Titzer, 'A Fast In-Place Interpreter for WebAssembly' (2022) shows a value stack + small control side-structures design hitting near-optimal interpreter speed; Erlang/BEAM (theBeamBook, scheduling & memory chapters) grounds the 'dying unit frees its whole heap/stack instantly because it shares nothing' model; Ertl & Gregg (JILP 2003) grounds keeping frames small enough that push/pop is a few stores, since frame traffic sits on the interpreter's critical path at every call.

## Inner loop discipline: no frame push/pop per token; TCO by frame reuse; delete the traced_word/TraceEnd dance [settled-practice]
The skeleton pops an Eval frame and re-pushes its continuation for EVERY token (runtime.rs step()/Frame::Eval), i.e., two Vec operations plus a large enum move per token. The real interpreter should hold (code, ip, env) in locals and run a tight fetch-dispatch loop over the current quotation; the frame stack is touched only when (a) a word call pushes a return frame, (b) a combinator suspends, (c) a body returns (pop). TCO becomes the classic discipline: when the fetched token is a call in tail position (ip == len after fetch) and the current frame owns no pending work, do not push a return frame — overwrite the in-register (code, ip, env) with the callee's body and continue. `if`/`call` in tail position inherit this for free because they merely replace the current code with the chosen branch. This entirely deletes the skeleton's traced_word/TraceEnd inheritance machinery (runtime.rs:341–397), which exists only because trace maintenance is eager — with lazy traces (next item) tail-call = frame overwrite, full stop. Recursion combinators (fold/each/while) already iterate via self-replacing frames; keep that pattern but with base-index frames.
GROUNDING: Proper-tail-call-as-frame-reuse is settled Scheme implementation practice (Clinger, 'Proper Tail Recursion and Space Efficiency', PLDI 1998 formalizes the space guarantee ecl's decision 10 is making); the CEK machine's tail rule (Felleisen/Friedman; re-derived in Ager–Biernacki–Danvy–Midtgaard 2003) is precisely 'don't grow K in tail position'. On loop mechanics: Ertl & Gregg (JILP 2003) and the CPython 3.14 tail-call interpreter work (Ken Jin; Nelhage's 'Performance of the Python 3.14 tail-call interpreter'; Haberman's musttail essays; wasm3's Interpreter.md meta-machine) all treat 'keep ip/sp in registers, minimize per-instruction memory traffic' as the first-order term — ecl doesn't need their musttail/threaded dispatch (per-token dispatch is explicitly allowed to be slow), but it must not pay a frame push+pop+128-byte move per token, which is an order worse than even switch dispatch.

## Trace machinery: lazy reconstruction at unwind time; provenance in code-object side tables, not on values or in a live trace vector [strong]
Adopt zero-cost traces: delete the live `trace: Vec<Arc<str>>` that is pushed/popped on every word call (runtime.rs:602–630) and the TraceEnd frames. Instead: (1) promote quotations-being-executed to lightweight code objects (the plain list plus interned metadata: qualified word name when the code is a word body, and a token-index → SourceSpan side table built by the reader); (2) frames already reference their code + ip, which is all a trace needs; (3) when an error actually unwinds, walk the frame stack once from the failing point to the catching boundary, mapping each word-body frame to its qualified symbol (innermost first) and taking the innermost failing token's span from the side table. Happy path pays literally nothing for traces. Measure-shaped argument: the eager scheme costs ~2 Vec ops + an Arc clone/drop per word call (executed millions of times per second) plus TraceEnd frame traffic; the lazy scheme costs one O(depth) walk per error, errors are rare by crash-only design (decision 7), and depth is bounded because TCO collapses tail chains. Both schemes lose tail-called words from the trace equally (the skeleton pops trace on tail calls too), so observable output is unchanged. This also moves `span` OFF runtime values (value.rs:35–38 puts a 32-byte Option<SourceSpan> on every Value): provenance is a property of code tokens, kept in the reader-built side table keyed by token index — exactly PEP 657's design.
GROUNDING: CPython 3.11 zero-cost exception handling (cpython InternalDocs/exception_handling.md; issue #84403): try becomes a NOP, an exception table on the code object is consulted only when raising, and the traceback is built frame-by-frame during unwind by PyTraceBack_Here — the canonical 'happy path pays nothing, unwind reconstructs' precedent. PEP 657 (Python 3.11): per-instruction source positions live in a compact side table on the code object and are decoded only when rendering a traceback — the exact model recommended for ecl provenance. JVM: Throwable captures a compact internal backtrace and materializes StackTraceElements lazily on getStackTrace (JDK-8150778; StackWalker API added for lazy frame access) — production proof that trace materialization belongs at observation time. Itanium-style table-driven unwinding in C++ is the same doctrine at the native level.

## attempt/spawn boundary frames and O(1) unwinding [strong]
Make attempt/spawn/module/dict-of boundaries explicit boundary frames recording {saved data-stack depth, saved frame-stack depth, link to previous boundary}. Maintain a register holding the innermost boundary's frame index (boundary frames form an intrusive singly-linked chain, like nested cancel scopes). Error unwind then: walk frames top→boundary once to build the lazy trace, truncate frame stack to the boundary, truncate data stack to its saved depth, push the {'err dict} outcome. This replaces catch_attempt's O(frames) rposition scan + Frame::remove (runtime.rs:729–745). Because ecl is crash-only with no finally/handlers/restarts (decisions 7, Rejected), unwinding never interprets intermediate frames — it is pure truncation, which is what makes error = 'unwind unit frames wholesale' honest. `attempt` should be the in-unit fast path (boundary frame, no scheduler involvement); `spawn` allocates a fresh unit with its own stacks and a write-once outcome cell; the ledger's 'attempt ≡ spawn await' is an observational-equivalence claim to preserve, not an implementation instruction to follow literally. Cancellation delivers through the identical unwind path with {'kind 'cancelled}, truncating to the unit root.
GROUNDING: CPython 3.11's exception-table unwinding (InternalDocs/exception_handling.md) demonstrates handler location via lookup rather than per-frame scanning; Trio's cancel scopes (trio reference-core docs; njs 'Timeouts and cancellation for humans') are the named precedent for a nested chain of boundary scopes where the innermost applicable one catches; Erlang/BEAM grounds crash-only wholesale discard (a dying process's heap and stack are freed instantly, nothing is interpreted on the way down — theBeamBook) and ecl's 'failed unit leaves nothing' is exactly a BEAM process death scoped to a substack.

## Data stack representation and stack caching [strong]
One contiguous growable array (Vec) of inline fat values per unit, growth-doubling, no segmentation. Shrink Value from the skeleton's ~56 bytes (24-byte kind + 32-byte inline Option<SourceSpan>) to a 16–24 byte tagged word: 8-byte payload (i64 / f64 / codepoint / interned symbol id / pointer to heap list/dict/string) + tag/flags, with the span field deleted per the provenance recommendation. Do NOT implement Ertl-style TOS-in-register stack caching in v1: the ledger explicitly says per-token dispatch never needs to be fast, stack caching complicates every primitive, and its payoff is precisely in the per-token regime ecl deliberately doesn't optimize. Keep the stack a plain indexable array so stack caching remains a compatible later move if profiling of scalar-heavy REPL code ever demands it (it would slot into the seal layer's threaded-code form naturally). Underflow checks against the current boundary's base index (one compare) also give decision 14's contract checks for free: a combinator iteration's effect check is 'depth-above-base == expected'.
GROUNDING: Ertl, 'Stack Caching for Interpreters' (PLDI 1995) quantifies the technique and its cost (specialized interpreter copies per cache state) — cited here as the thing to consciously defer, with the paper's own framing that it targets per-instruction argument-access overhead, which ecl's K-style amortization model (Whitney's K/J; decision 21) makes a non-goal; Factor (DLS 2010) and wasm3 (Interpreter.md, 64-bit slot stack) both run production concatenative/stack code on contiguous slot stacks with fat/uniform cells; Titzer's wasm interpreter paper reports a contiguous value stack as the fast layout for an in-place interpreter.

## Safe points: reduction-counter polling fused with the cancellation flag; kernels poll chunked [strong]
Give each unit a fuel counter (à la BEAM reductions) decremented at word calls and loop back-edges (while iterations, combinator iterations), and a per-unit atomic cancellation flag set by the scheduler/parent. Poll site = the fuel decrement: when fuel hits zero, check cancellation (and any future preemption/GC handshake), refill, continue. This makes 'cancellation lands at frame boundaries' concrete and bounds delivery latency by one poll interval. Critical addition the ledger doesn't state: coarse kernels over huge flat leaves (a fold over 10^9 i64s is ONE runtime loop, by design) would otherwise be uncancellable for seconds — kernels must poll the flag every N elements (N ~ 64K–1M, chosen so poll cost is noise) or be internally chunked. Cancellation observed at a poll raises the standard unwind with {'kind 'cancelled} through the same boundary-frame truncation path as errors; because values are immutable and units share nothing mutable, stopping at any poll point is safe (nothing torn). Coordinate with the scheduler area: the flag is the only cross-thread signal into a running unit; blocking ops (await, IO) are their own checkpoints.
GROUNDING: Erlang/BEAM reduction counting (theBeamBook scheduling chapter): processes are preempted only at safe points (function calls) via a ~2000–4000 reduction budget, cooperative at the C level, preemptive at the language level — the exact mechanism recommended; Trio's checkpoint discipline (trio reference-core docs; njs 'Timeouts and cancellation for humans' / 'Notes on structured concurrency') establishes 'every blocking/await point is a cancellation checkpoint and delivery is guaranteed at checkpoints', the semantics ecl's safe points must provide; Tokio's cooperative task budgeting is the same idea in a work-stealing runtime. BEAM's per-process heap freeing grounds the discard-wholesale half.

## Dispatch and binding lookup on the frame machine's hot path [strong]
v1: intern all word names to u32 symbol ids at read time; primitive dispatch becomes a match on a dense primitive-id (the skeleton's string-match `primitive(&str)` with a `word.contains('.')` test per resolution must not survive). Environment resolution results must not be cloned per call (the skeleton clones a Binding out of an RwLock per word execution); resolve to a reference-counted binding cell and, for module words, hold the registry-generation indirection so hot reload keeps working. Do NOT add inline caches or quickening in v1 — but keep the enabling invariants: binding writes are already observable events (ledger requirement), which is exactly the invalidation hook quickening/inline-cache designs need; the deferred seal layer's 'cached compiled form' is where Brunthaler-style quickening and CPython-PEP-659-style specialization belong, rewriting a word's body into a threaded array of resolved handler+operand pairs at seal time (allowed: 'internal threaded/opcode arrays at most').
GROUNDING: Brunthaler, 'Efficient Interpretation using Quickening' (DLS 2010) — rewrite instructions to specialized forms after first execution, with invalidation on redefinition; CPython PEP 659 (specializing adaptive interpreter, 3.11) — adaptive specialization with version-tag invalidation on dict/binding writes, the production model for 'late binding is semantics, caching is an event-invalidated optimization'; Ertl & Gregg (JILP 2003) for threaded-code arrays as the compiled form; the CPython 3.14 tail-call interpreter and wasm3/upb musttail work (Haberman) as the ceiling for dispatch technique should ecl ever need it — noted and deliberately deferred because decision 21 caps compiled forms at threaded arrays and the K model makes dispatch a non-bottleneck.

## Host error propagation mechanism [judgment-call]
Keep Rust Result as the unwind vehicle inside the machine (the skeleton's Result<(), EclError> step signature is correct — no panics, no host exceptions, satisfying 'no host exception ever leaks'), but box the error payload (Result<(), Box<EclError>>) so the happy-path return value stays register-sized; EclError with its Vec/String fields is large and currently taxes every primitive return. Convert host IO errors to error dicts only at the IO boundary words, as the skeleton already does (keep that).
GROUNDING: Standard Rust performance practice for error-heavy Result plumbing (rustc itself boxes large error types); consistent with the CPython zero-cost doctrine of making the no-error path pay nothing — here the 'cost' is the by-value move of a large error struct through every frame-machine return.

CONFLICTS:
* Ledger wording vs lazy traces: DESIGN.md's Runtime section says 'The machine maintains the ecl-level trace (qualified words + provenance) for error dicts'. Read literally ('maintains'), that mandates the skeleton's eager scheme, which taxes every word call. The recommendation (reconstruct from frames only at unwind) satisfies every observable requirement of decision 19 while paying nothing on the happy path — but the ledger sentence should be amended to 'the machine can produce the trace at any unwind point' so the eager reading doesn't get re-implemented later as a 'fix'.
* Guaranteed TCO vs complete traces (inherent, ledger should document): frame reuse erases tail-called words, so a trace shows only the non-tail spine (a deep tail-recursive loop appears as one frame). The skeleton's eager scheme has exactly the same behavior (it pops trace entries at tail calls), so nothing regresses — but decision 19's 'trace: list of qualified word symbols, innermost first' silently means 'the non-tail-call chain', and that should be stated. (Same trade every proper-TCO language makes; cf. Scheme, and CPython's frame-per-call traces being possible only because Python refuses TCO.)
* 'attempt ≡ spawn await' vs performance: implemented literally, every attempt would allocate a unit and cross the scheduler. Recommendation treats the equivalence as observational (attempt = in-unit boundary frame; spawn = real unit), which the ledger's phrasing permits but does not spell out — worth a ledger note so the equivalence is preserved as a test property, not an implementation.
* Cancellation at safe points vs coarse kernels (real gap): decision 21 requires kernels to run as single fat loops over leaves; decision 20/Runtime says cancellation lands at frame boundaries. A fold/pervasive-add over a multi-GB leaf has NO frame boundary for seconds — unbounded cancellation latency. The scheduler and kernel areas must agree on chunked polling inside kernels (flag check every N elements); the ledger currently doesn't acknowledge kernels as safe-point deserts.
* Share-nothing parallel units vs reference-counted shared values (cross-area, affects the frame machine's hot path): 'immutable values shareable across units with no copying' + 'no GIL' forces the sharing metadata (refcount/uniquely-held bit, decision 1's CoW) to be thread-safe. Plain atomic RC taxes every stack dup/drop the frame machine executes. The value/memory area should own this (candidates: biased reference counting, Choi et al. OOPSLA 2018; Perceus-style precise RC with reuse, Reinking/Xie/Leijen PLDI 2021; or BEAM-style copy-on-send for small values with refc only for large leaves, which would contradict the 'no copying' claim) — flagging because the chosen answer determines the cost of every push/pop/dup the frame machine performs.
* Per-iteration child environments vs kernel model (skeleton vs ledger, resolved in recommendations): the skeleton allocates an env per combinator element to enforce quotation self-containment, but decisions 6/14 make quotations capture nothing and dict-of is the only construct requiring a child env for names — combinator iterations need stack isolation (base index), not env allocation. If some future semantics genuinely requires a fresh env per element, it conflicts with 'combinator loops are single kernel loops' and must be settled in the ledger.

## SIMD strategy under 'no JIT ever': three tiers, all ahead-of-time [settled-practice]
Adopt a three-tier SIMD strategy, all of it AoT-compiled so decision 21 is never touched. Tier 1 (v1, mandatory): write every kernel as an autovectorization-friendly scalar loop over flat leaves — contiguous indexed loops over &[i64]/&[f64], no per-element Result, no per-element enum dispatch, no function-pointer ops (monomorphize per (op, leaf-type) pair), error detection accumulated as a mask and checked per block, not per lane. Compile the interpreter with a modest baseline (x86-64-v2 / NEON) and let LLVM vectorize. Tier 2 (when profiling demands): explicit portable SIMD for the loops autovectorizers reliably miss (compress/where, packed comparisons, radix histograms, overflow-checked int arithmetic) using stable-Rust mechanisms only — safe target_feature intrinsics (stable since Rust 1.87) wrapped by the `multiversion` or `pulp` crate. Do NOT depend on nightly std::simd: as of early 2026 it is still nightly-only with no stabilization timeline (portable-simd issue #364), and pinning a language runtime to nightly is unacceptable. Tier 3 (dispatch): per-ISA kernel variants compiled ahead of time and selected once at startup/first-call via cpuid — exactly Google Highway's HWY_EXPORT/HWY_DYNAMIC_DISPATCH function-pointer-table model and GCC/ISPC function multiversioning; `multiversion`'s 'direct dispatch' mode is the Rust equivalent. This is the same architecture CBQN ships: SIMD exists only inside pre-written kernels (generated via Singeli, compiled to C ahead of time), and CBQN names 'code using SIMD and other special instruction sets' as a major performance factor while remaining a pure interpreter. Kernel variants are data, not generated code — no conflict with 'interpreted permanently'.
GROUNDING: Google Highway README/FAQ (github.com/google/highway): 'performance-portable, length-agnostic SIMD with runtime dispatch'; dynamic dispatch compiles one version per target via foreach_target.h re-inclusion and dispatches through a function-pointer table — replicating only the SIMD kernels, not the binary. CBQN (github.com/dzaima/CBQN) + Singeli (github.com/mlochbaum/Singeli): ~5k lines of Singeli-generated SIMD kernels in production; mlochbaum.github.io/BQN/implementation/perf.html lists SIMD kernels among the major speed factors of an interpreter with no JIT. ISPC (Pharr & Mark, InPar 2012, llvm.org/pubs/2012-05-13-InPar-ispc.html): the AoT SPMD-on-SIMD precedent — per-target code generated ahead of time. Rust state: Shnatsel, 'The state of SIMD in Rust in 2025/2026' (shnatsel.medium.com) and rust-lang/portable-simd issue #364 confirm std::simd is nightly-only with blocking API issues; docs.rs/multiversion and lib.rs/pulp document stable runtime-feature-detected multiversioning (pulp powers faer).

## Kernel loop-shape rules forced by ecl's error semantics (overflow/NaN as errors) [strong]
Decision 4 (int overflow errors) and decision 22 (NaN is 'domain, finite→inf is 'overflow) must not force scalar per-element branching. Structure every arithmetic kernel as: compute the whole block with wide ops, accumulate a fault mask (int overflow via sign-logic/widening checks, float via NaN/inf lane tests on the results), test the mask once per block (e.g. every 64–512 elements), and only on a hit re-run that block scalar to identify the faulting element for the error dict ('data with index, 'word, provenance). This is legal precisely because ecl is crash-only with transactional units: an error discards the whole unit's substack, so computing past the fault point is unobservable — immutability guarantees no partial result leaks. The two-pass 'compute wide, diagnose slow' pattern is standard in checked-SIMD code and is what keeps ecl's unusually strict numeric semantics compatible with vectorization. Comparison kernels emit 0/1 masks with no fault path and vectorize trivially; and/or/not on 0/1 ints likewise.
GROUNDING: The crash-only + rollback design in DESIGN.md decisions 7/10 is what licenses this (speculative wide execution with deferred error identification); CBQN uses the same select-algorithm-by-inspecting-arguments and blockwise strategies (mlochbaum.github.io/BQN/implementation/perf.html); kdb+ takes the opposite route (wrapping/promoting arithmetic) which ecl rejected, so ecl needs this mask-accumulation discipline where K needs none. Highway and portable-SIMD APIs provide the mask-reduction ops (AllTrue/any) this pattern needs.

## Which VOCABULARY.md kernels are SIMD-profitable, and by how much [strong]
Rank the ~40 kernels by SIMD payoff and spend effort top-down. (1) Pervasive arithmetic/comparison on i64/f64 leaves (+,-,*,/,min,max,=,<,...,neg,abs,floor): 4–16x on cache-resident data, compressing toward 1–3x at DRAM sizes where bandwidth caps everything (roofline) — but note the biggest v1 win here is 10–100x from flat leaves replacing the skeleton's boxed values, before any SIMD. (2) Boolean mask ops (and/or/not on masks) and mask consumers: trivially SIMD; see the conflicts section on mask representation — CBQN's packed bit-booleans are one of its named major speed factors and ecl's i64 masks forfeit up to 64x of that. (3) Reductions sum/min/max/any/all (via recognized fold idioms): classic SIMD, 4–8x cache-resident; kdb+ 4.0 explicitly lists sum/avg/max/min among its multithreaded (and vectorized) aggregates. (4) where (mask→indices): vectorizable via compress-store (AVX-512 VPCOMPRESSD) or byte-lookup tables — BQN's replicate/indices notes cover the algorithms; several-fold speedups. (5) take/drop/reverse/cat/at-with-index-vector/copy: memcpy/gather-class — 'K is fast because memcpy is fast' (DESIGN.md quotes the model); mostly free via libc memmove, plus a SIMD gather for at. (6) grade: LSD radix sort with SIMD histogramming for i64/char leaves — BQN's sort notes: radix pays above ~100 elements ('use 1-byte counts and sum with SIMD or at least SWAR'), sorting networks are SIMD-suitable for small arrays; expect 5–20x over comparison sort. (7) Low value: dict align/merge, string search/split (memchr-class helps split), generic-spine recursion — leave scalar.
GROUNDING: mlochbaum.github.io/BQN/implementation/primitive/sort.html (radix threshold ~100, SIMD/SWAR counts, SIMD sorting networks); mlochbaum.github.io/BQN/implementation/primitive/fold.html (+/⌈/boolean folds 'suitable for SIMD implementation', carry-fixup technique for scans); mlochbaum.github.io/BQN/implementation/perf.html (packed bit-booleans + SIMD as major factors); code.kx.com/q/kb/mt-primitives/ (the exact atomic/aggregate list kdb+ found worth optimizing); Williams, Waterman & Patterson, 'Roofline: An Insightful Visual Performance Model for Multicore Architectures', CACM 52(4) 2009 (why elementwise ops at ~0.06–0.25 ops/byte are memory-bound at scale).

## Float reduction determinism: one fixed association tree shared by every execution path [strong]
Define, now, a single reduction association for float sum/fold-class kernels that depends only on data length — e.g. fixed-width blockwise: lane-strided partial sums within a 64- or 128-element block, blocks combined left-to-right — and make the scalar kernel, the SIMD kernel, every ISA variant, and any future multicore split all produce bit-identical results by construction (multicore splits at block boundaries, partials combined in index order). Without this, (a) idiom-recognizing a user's `0 (+) fold` into a SIMD sum kernel silently changes float answers vs the frame-machine left fold — breaking 'recognition is semantically invisible'; (b) level-2 multicore results would depend on thread count — breaking the ledger's 'deterministic result, still one unit' requirement; (c) ISA-variant selection at startup would make answers machine-dependent. The cheapest coherent choice: specify float fold/sum as blockwise-associated (document it — IEEE addition is not associative, so this is a real semantic commitment), and have the frame-machine fallback for `(+) fold` on float leaves defer to the same kernel. Integer and min/max reductions are associative and exempt (int sum still needs the overflow-mask discipline).
GROUNDING: mlochbaum.github.io/BQN/implementation/primitive/fold.html discusses SIMD fold/scan structure (per-unit partial results + carry combination) — the same fixed-tree idea; kdb+ mt-primitives (code.kx.com/q/kb/mt-primitives/) parallelizes sum/avg across secondary threads, which is exactly the reassociation hazard this rule pre-empts; the roofline/HPC literature on deterministic parallel reductions (fixed blocking independent of worker count) is the standard remedy. DESIGN.md's own level-2 requirement ('semantically invisible... deterministic result') forces some such rule; none is currently written down.

## Kernel-internal multicore (level 2): defer the implementation, bake in the shape; roofline says when it pays [strong]
Do not implement level-2 multicore in v1, but write every kernel against a splittable signature from day one: kernel(op, leaf-slices, output-range) operating on an explicit index range, so a future splitter can fork block-ranges without touching kernel bodies. When it lands, copy kdb+ 4.0's envelope exactly: activate only above a grain threshold on the order of 10^5 elements per worker (kdb+'s published figure), only for the ops where extra cores buy bandwidth or compute (aggregates, elementwise on multi-channel-memory machines, radix passes), keep it semantically invisible (one unit, deterministic split per the fixed-association rule), and stay single-socket by default (kdb+ 4.0 is explicitly not NUMA-aware and recommends numactl pinning). Roofline reality check: elementwise arithmetic at ~1 op per 8–24 bytes sits far below the ridge point, so one core (~20 GB/s) cannot saturate a modern socket (~100–400 GB/s multi-channel) — multicore pays roughly (socket bandwidth / single-core bandwidth) ≈ 2–6x on DRAM-resident arrays and approximately nothing on cache-resident ones; compute-dense kernels (pow, sqrt, sort, group) scale closer to core count. This is also the honest explanation of why K stayed essentially single-threaded per query for decades: primitives were single-threaded until kdb+ 4.0 (2020); parallelism lived at the coarse layer (peach over partitions, multiple processes), which was simpler, deterministic, and captured most of the win for partitioned workloads — kx added within-primitive threading only when many-core, multi-channel servers made all-core bandwidth the resource worth harvesting ('intended to exploit all-core memory bandwidth'). ecl should follow the same sequencing: fat single-threaded kernels first, level 2 only when profiling shows DRAM-resident arrays dominating.
GROUNDING: code.kx.com/q/kb/mt-primitives/ ('minimum amount of data processed per thread... on the order of 10^5 vector items', 'same secondary threads as peach', all-core bandwidth rationale, ~110 GB/s socket vs <20 GB/s core, NUMA caveat); code.kx.com/q/basics/peach/ and code.kx.com/q/releases/ChangesIn4.0/ (primitives single-threaded pre-4.0; 4.1 removed the no-nesting-inside-peach limitation); Williams/Waterman/Patterson Roofline, CACM 2009 (memory-bound vs compute-bound crossover).

## Idiom recognition: the only bridge from user-composed code to the vector unit [strong]
Given no JIT, the ONLY way `(1 +) each` or `0 (+) fold` reaches a SIMD kernel is recognition at combinator entry. Implement it as: when each/zip-with/fold/scan receives a specialized leaf plus a quotation, structurally match the quotation against a small table of shapes ((w) for primitive w; (k w) / (w k) for constant-operand forms; (0 (+) fold)-style compositions for sum/prod/mean), then verify each word in the matched shape currently resolves to the expected primitive binding in the application environment — this env check is what makes recognition sound under late binding (a user re-`def`ing `+` must defeat the fast path; per DESIGN.md, binding writes are observable events, so a recognition cache keyed on binding generation is the later optimization, but v1 can just do the lookup per application — the quotation is a handful of tokens, the cost amortizes over the whole array, exactly the 'per-token dispatch never needs to be fast' bet). On match: run the vector kernel over the leaf. On no match: the frame-machine per-element path, unchanged semantics. This is exactly Dyalog's idiom recognition (specially recognized phrases executed as single primitives, 2–4.5x reported; recognition is exact — near-miss phrases fall back) and K's special-casing of +/ etc.; ecl's homoiconic quotations make it easier than APL's, because the 'phrase' is already a first-class list to pattern-match, and decision 14's per-application contract check gives a natural hook point. Coordinate with the kernels area: the recognition table and the kernel registry must be one artifact so adding a kernel automatically adds its idiom. The deferred seal layer later turns per-application recognition into cached compiled form — same table, checked once.
GROUNDING: Dyalog Idiom Recognition (help.dyalog.com/13.1/.../Idiom Recognition.htm; course.dyalog.com/Interpreter-internals/): idioms 'treated as individual tokens and executed with special code', speedups 2–4.5x, recognition precise with fallback; mlochbaum.github.io/BQN/implementation/primitive/fold.html (arithmetic folds as the canonical special-cased combinator+function pairs); DESIGN.md decisions 9/14/21 (plain-list quotations, observable binding writes, per-application dynamic contracts) supply the invalidation and hook mechanics.

## par-each grain size: transparent chunking is conformant; no runtime warnings [judgment-call]
Do not warn on tiny-grain par-each and do not add a nag heuristic — a calculator that lectures is off-brand, and the real defense against 'par-each for arithmetic' is level-1 kernels being so fast that level 3 visibly loses. Do two things instead. (1) Docs-culture with the kdb+ framing: document par-each as 'coarse, heterogeneous, IO-bound grains, ~µs+ each' with the elementwise-arithmetic antipattern called out explicitly (kdb+'s peach docs and community guidance carry exactly this culture: vectorized primitives everywhere, peach at partition/query grain). (2) Reserve the right to chunk: the ledger already makes chunked or even serialized execution of par-each observationally conformant — outcome order is program order, leftmost-'err re-raise is deterministic, cross-task IO interleaving is explicitly unspecified, and a failing par-each cancels unawaited siblings anyway, so no program can rely on every element having run. Therefore a later [P] override of the prelude par-each that spawns ~ncores chunk-tasks over index ranges instead of one task per element is a pure optimization. Ship the prelude spawn-per-element version in v1 (it is the semantic spec), and let the scheduler's task-creation cost target be 'cheap enough that a µs grain amortizes' rather than 'cheap enough for elementwise use'.
GROUNDING: code.kx.com/q/basics/peach/ (peach positioned for coarse independent work over secondary threads; per-thread grain guidance) and code.kx.com/q/kb/mt-primitives/ (the implicit level handles the fine grain, with an explicit ~10^5-item threshold — i.e., kx also chose thresholds over warnings); DESIGN.md decision 20's determinism clauses are what make transparent chunking legal; Cilk-descended work-stealing practice (grain size chosen so steal overhead amortizes) is the standard framing the docs should teach.

## Pool unification: one worker pool under both the unit scheduler and kernel splits [settled-practice]
Build ONE work-stealing worker pool sized to physical cores, owned by the runtime, from day one — even while level 2 doesn't exist — and route both levels through it when it does: units (level 3) are scheduled tasks on the pool; kernel-internal splits (level 2) are scoped fork-join subtasks on the same pool with the calling worker participating in its own split (so an idle machine gives a lone big kernel all cores, and a machine busy with units gives it few — graceful adaptation instead of oversubscription). Never let a kernel own threads. The failure mode being designed out is the classic two-pool composition disaster: OpenMP-inside-TBB style nested mandatory parallelism causing exponential thread creation and oversubscription (documented at length in the TBB composability literature and Malakhov's composable-threading work), and its Rust incarnation, rayon-inside-tokio ('every library has its own thread pool, the CPU is wildly oversubscribed... don't mix them, bridge them'). kdb+ is the direct array-language precedent for unification: multithreaded primitives 'execute in the same secondary threads as peach' — one pool, two levels — with 4.0 forbidding nesting them and 4.1 making them compose. Two design consequences: (a) blocking points (await, IO) must not park pool workers — either give units a separate small blocking-aware scheduler layer that dispatches CPU work to the pool (tokio's spawn_blocking split, inverted), or make await a scheduler yield point since units are already frame machines that can suspend between frames — the frame machine makes green-thread-style unit multiplexing natural; (b) kernel splits must be pure, non-blocking, bounded work items (they are, by construction — pure kernels over immutable leaves), so they can never deadlock the pool. Cancellation stays at level 3 only: kernel splits are invisible and uncancellable mid-block; a cancelled unit is discarded at the next frame-boundary safe point after its kernel call returns.
GROUNDING: code.kx.com/q/kb/mt-primitives/ ('the same secondary threads as peach'; one -s pool serving both implicit and explicit parallelism) and code.kx.com/q/releases/ChangesIn4.1/ (nesting made composable); Voss/Asenjo/Reinders TBB composability chapter ('The Pillars of Composability', Springer) and Malakhov et al., 'Composable Multi-Threading and Multi-Processing for Numeric Libraries' (SciPy 2018) on nested-parallelism oversubscription; blog.dureuill.net 'Mixing rayon and tokio for fun and (hair) loss' + docs.rs/rayon (one global pool; fork-join with caller participation) for the Rust-specific failure mode and the scoped-join model; Blumofe & Leiserson-lineage work stealing (Cilk) for caller-participates fork-join.

CONFLICTS:
* Float fold determinism vs idiom recognition and level-2 multicore: DESIGN.md nowhere specifies the association order of float reductions, but (a) recognizing `0 (+) fold` into a SIMD/parallel sum kernel reassociates IEEE addition and changes answers vs the frame-machine left fold, and (b) level 2's 'semantically invisible, deterministic result' promise is violated by any thread-count-dependent reduction tree. The ledger must gain a ruling: float reductions are blockwise-associated with a block size fixed by data length (shared by scalar, SIMD, all ISA variants, and multicore splits), or float folds are excluded from recognition and level 2. Without the ruling, either recognition is unsound or the fallback and fast paths disagree.
* Startup ISA selection vs cross-machine determinism: per-ISA kernel variants (the recommended AoT dispatch) can only be deterministic across machines if every variant of a float kernel implements the identical association tree. This is achievable (fix the tree, vary only the lane width used to walk it in lane-invariant order) but must be stated as a kernel-authoring invariant; the ledger's determinism language currently only contemplates one machine.
* Leaf type set (i64/f64/char only, decisions 2/21a) vs mask bandwidth: ecl comparison masks are 0/1 int64s — 8 bytes/element — while CBQN names packed bit-booleans as a major performance factor (up to 64x less bandwidth on mask pipelines like `dup 0 > where at`). Adding a hidden packed-bool or i8 leaf kind is representation-only and semantically invisible (it still prints as specialized [..] per decision 16), but it is not in the ledger's enumerated leaf set; recommend reserving the leaf-kind slot now even if v1 ships i64 masks, because retrofitting a leaf kind touches every kernel signature.
* par-each ([E], spawn-per-element per VOCABULARY.md) vs grain economics: one task per element at ~µs task cost is pathological on large vectors. No semantic conflict — the ledger's own determinism clauses (program-order await, leftmost-'err, unspecified cross-task IO interleaving, sibling cancellation on failure) make transparent chunking observationally conformant — but it means par-each's prelude definition is a spec, not the implementation, and the runtime needs license (a [P] override) to chunk. Worth a one-line ledger addendum so nobody later argues the prelude text forbids chunking.
* 'No GIL-shaped design' + share-nothing units vs a single unified worker pool: unification means unit execution and kernel splits share threads, so a unit blocked in await must suspend at a frame boundary (green-thread style) rather than park a pool worker, or the pool starves. This is compatible with the frame machine (suspension between frames is natural) but constrains the scheduler design: await/IO must be yield points, not thread blocks — a requirement the ledger implies (cancellation at safe points) but does not state for blocking.
* Inter-area coordination: the idiom-recognition table and the kernel registry must be one artifact owned jointly with the kernels/dispatch area — a kernel without an idiom entry is unreachable from user-composed each/fold code (no JIT means no other bridge), and an idiom entry without a kernel is a silent fallback. Also, recognition soundness depends on the environments area delivering cheap 'does word w currently resolve to primitive p' checks and binding-generation counters (the ledger's 'binding writes are observable events').

===== CRITIC: minimalist =====

OBJECTIONS:
* CUT the cached execution view (dispatch bundle, v1). It violates the plain reading of decision 10 ('No bytecode VM unless profiling demands one') — the bundle itself admits it needs a ledger ruling — and it drags four mechanisms into v1: a memoized view slot in every list header, OnceLock thread-safety for that slot, view invalidation on in-place slack append, and per-call-site indices whose only purpose is to mount stage-2 inline caches. Worse, the wins credited to the view (no per-token Value+span clone, no string hashing, no RwLock probe) are actually delivered by three simpler changes the bundles already mandate: interned u32 words, spans off Value, and lock-free env snapshots. After those, walking the plain quotation list is a load + match per token — exactly what the doctrine says is enough, and exactly what K and J do. The view IS the seal layer's 'cached compiled form' (d.21d); build it there, later, once, or never.
* CUT three of the environments bundle's four invalidation mechanisms. It proposes ArcSwap binding cells + per-env shape epochs + per-module generation counters + a watcher-callback system — four ways to observe binding writes, feeding inline caches and quickened shadows that don't exist in v1 and shouldn't. The bundle's own conflicts section quietly concedes the right v1 ('plain list-walking plus cells+versions as substrate'), contradicting its recommendations. Ship: env tables as immutable snapshots keyed by u32 id (2-3 chain probes per word — unmeasurable on array workloads), module registry as name -> atomically-swapped generation (this alone is hot reload AND the sufficient 'binding writes are observable' event), and nothing else. The ledger requires writes to be observable events, not a subscription framework; one monotonic counter bumped on write satisfies it. Watchers, shape epochs, and per-(body, resolution-env) quickened shadow arrays — a cache keyed on a cross product that even CPython avoids (it caches per code object, not per (code, globals) pair) — are all seal-layer-or-never.
* CUT stage-2/stage-3 dispatch machinery entirely, including the 'uniform handler signature' hedge for Rust musttail. The bundles' own evidence kills it: corrected CPython 3.14 tail-call gains are 1-5% geomean in a bytecode-BOUND language, and ecl is kernel-bound by design. Designing v1 handler signatures around a nightly Rust feature (become, rust#112788) that the same bundle predicts will never show up in profiles is carrying dead weight. Same verdict for static superinstructions and view-build-time idiom recognition. The K/J/BQN lineage shipped fast interpreters with ZERO inline caches, superinstructions, or quickening — array languages don't execute enough tokens for any of it to matter. The doctrine 'per-token dispatch never needs to be fast' means you never build these, not that you build the mounting brackets for them. 'Staged plan' items are not free: a one-maintainer project's roadmap IS its complexity budget, and every 'reserved/stage 2' entry is a design constraint someone must honor forever.
* DEFER the custom bucket allocator; store capacity explicitly instead. The values bundle claims '~200 lines' for the size-class layer, but the scheduler reality (truly parallel units) means per-thread freelists + a global reservoir + remote-free handling — that's a concurrent allocator, mimalloc territory, the highest-risk subsystem in the whole plan. K's allocator is tiny because K is SINGLE-THREADED; the ledger's no-GIL mandate breaks the analogy the recommendation leans on. The 'capacity derived from bucket class' trick saves one u32 in the header at the price of writing and debugging an allocator before the language works. Ledger invariant 21(b) requires slack capacity and amortized O(1) append — an explicit cap field in the header over mimalloc/system malloc satisfies it identically. The Whitney aesthetic of allocator-is-the-representation is real, but it's the LAST thing he'd tell one maintainer to build first.
* DELETE the biased-RC owner byte, the escape-promotion (mark-on-share) design, and the shared-across-units flag from the v1 header. Both the values and scheduler bundles correctly conclude plain atomic RC is sound and amortized (push/pop do zero RC ops under the stack-ownership discipline; kernels do O(1) header ops), then reserve header layout and a promotion-walk design for an unmeasured problem anyway. Choi et al.'s 22.5% figure is from Swift, a language doing RC traffic on every method call — ecl's discipline removes the traffic instead. If atomic RC ever profiles, a header field is a relayout, not a rewrite. Speculative layout is complexity paid now for a payoff that the coarse-kernel model predicts never arrives.
* SIMPLIFY the dict. The CPython compact-ordered design with variable-width index tables (u8/u16/u32 growth) is CPython-scale engineering for a calculator whose dicts are mostly small and whose big dict IS the table-of-columns, iterated not probed. V1: keys vector + values vector (insertion order for free, and the columns literally are the table story) + cached hashes + linear scan below ~8-16 entries + one fixed u32 hash index above. Same asymptotics as the recommendation, half the machinery, and it reuses the list machinery you already built — a dict is two lists plus an optional index, which is precisely K's dict.
* COLLAPSE idiom recognition to ONE mechanism with one owner. It's currently proposed in three bundles with two incompatible placements: view-build-time Dyalog-style phrase rewriting (dispatch) vs combinator-entry structural match + resolution guard (kernels, vectorization). Keep only combinator-entry: match the quotation shape against a closed table of ~6 patterns ((+)/(*)/min/max for fold-scan, single pervasive word for each/zip-with), verify each word resolves to the expected core primitive at this application, run the kernel; else generic path. Per-application guard cost is O(quotation length) against O(n) work — no cache, no generation keys, no invalidation, sound under late binding by construction. The dispatch bundle's view-time recognition and the vectorization bundle's 'recognition cache keyed on binding generation' both die with this ruling. Also adopt the kernels bundle's requirement that the recognition table and kernel registry be one artifact.
* CHOOSE the boring float-fold semantics and delete the determinism apparatus. The vectorization bundle's 'fixed association tree shared by scalar, SIMD, every ISA variant, and future multicore splits' is a cross-cutting invariant every kernel author must honor forever, plus a ledger amendment blessing blockwise float addition. The kernels bundle already named the cheaper option: float folds are strict left folds on EVERY path (excluded from SIMD recognition); integer/min/max folds reassociate freely because exact. This costs float-sum throughput ecl's awk/sed positioning does not need, and deletes: the association-tree spec, the cross-ISA determinism invariant, the fused-vs-generic divergence risk, and the level-2 reduction-tree constraint. If float-sum speed ever matters, add a documented `fsum` word — a new word is cheaper than a new invariant.
* STRIP the scheduler to its v1 skeleton and stop designing level 2. Kernel-internal multicore ('level 2') appears nowhere in the ledger — it is the vectorization bundle's invention, and kdb+ itself waited ~20 years (until 4.0, 2020) to add it. Therefore: no unified worker pool 'from day one', no Tokio steal-half/throttling detail, no blocking-pool committed-evolution design, no timing wheels. V1 scheduler = N worker threads (with 1-worker degenerate config), one mutex-protected run queue, fuel counter fused with cancel-flag checks, mutexed write-once task cells with parked-unit waiter lists, one timer thread with a binary heap, Trio-style wait-for-quiescence at scope close. That's a weekend-scale subsystem instead of a runtime project. The only day-one concession to the future worth keeping is the splittable kernel signature (explicit index range) — it costs zero.
* DEFER SIMD tiers 2 and 3 without reserving anything. Tier 1 (autovectorization-friendly monomorphic loops, block-flag error accumulation, modest baseline compile flags) is the whole v1 story and is genuinely load-bearing. Tier 2 (pulp/multiversion explicit SIMD) and tier 3 (per-ISA variants + cpuid dispatch tables) add build-matrix complexity, a kernel-authoring DSL decision, and the cross-ISA float-determinism problem — all for throughput beyond what the positioning ('scripting fast', awk/sed slot) requires. CBQN needs Singeli because BQN competes as a fast array language; ecl's ledger explicitly does not (K-order is the eventual CEILING, not a v1 target). Revisit only when a real workload profiles memory-bound on tier-1 kernels.
* The combined six-bundle design exceeds one maintainer. Subsystem count as recommended: concurrent bucket allocator, intern table, execution-view cache + invalidation, inline caches + epochs + watchers + quickened shadows, work-stealing scheduler + timer wheel + blocking pool + cancellation tree, kernel macro generator + idiom table, SIMD tiers 2-3 + ISA multiversioning, compact dict, biased-RC/mark-on-share evolution paths. Whitney's whole K is smaller than any three of these. The v1 that honors every ledger invariant is: 16B tagged values; heap header {atomic rc, tag, len, cap}; flat leaves (i64/f64/char1/2/4/symbol) + generic spines; global append-only intern table; ONE match-loop frame machine with ip/code/env in locals, frame-reuse TCO, base-index substack rollback, lazy traces; env = chained u32-keyed snapshot tables + one generation counter; primitives as bindings; ~40 monomorphic kernels behind a match on (op, tag); combinator-entry recognition of ~6 idioms; mutex-queue scheduler with fuel and cancel flags. Everything else in these bundles belongs in an appendix titled 'if profiling ever demands', not in the plan.
* Minor but telling: the values and dispatch bundles disagree on what the header holds (values: rc/meta/len with capacity implicit; dispatch: rc + view slot + slack capacity), three bundles each independently design the intern table (Vec<Arc<str>> vs arena, RwLock vs sharded vs lock-free), and the environments bundle proposes both plain walking and full cell/epoch machinery in different sections. Six parallel researchers have produced overlapping subsystem designs with no reconciliation; the header layout, the intern table, and the recognition mechanism each need exactly one owner and one design before any code is written.

MISSING:
* Nobody owns the reader/code plane, and the provenance story has a hole: every bundle says 'spans move to a side table on reader-produced code lists', but no one specifies what keys that table once quotations are built at RUNTIME via cons/compose/parse (the ledger's entire metaprogramming story, d.8). A cons'd quotation is a new list with no reader spans — what does an error inside `3 (+) cons call` trace to? The side-table keying (list identity? word-body ownership? token index after splice?) and the no-span fallback behavior need a ruling before the trace design is real. Note the ledger's Boundary section says 'provenance attached to every token' — two bundles flag the conflict but no one writes the amended wording.
* No cold-start audit against the soul test. `ecl '3 4 +'` must answer instantly (d.21), yet the combined design starts N worker threads, a timer thread, interns the vocabulary, loads and executes the prelude module, and (per some bundles) builds recognition tables — at every invocation. Nothing in six bundles addresses lazy scheduler/timer spin-up (don't create workers until first spawn), prelude cost, or startup budget. This is the one performance number the ledger actually names, and it constrains the scheduler and module designs more than any throughput concern.
* Order-insensitive dict HASHING is unspecified. D.22 says dict equality ignores insertion order, and the values bundle requires hash to agree with = (citing the int/float case) — but that forces dict hashes to be commutative over entries (e.g. XOR/sum of entry hashes), which no bundle states, and which interacts with the cached-per-entry-hash design.
* The kernel matrix is never actually counted. 'About forty loops' is the vocabulary's number, but the recommendations multiply it: 3 char widths x pervasive ops, (i64,f64) mixed-promotion variants, scalar-operand variants for each binary op, plus fused fold/scan/filter kernels. Nobody states the real monomorphic-loop count (plausibly 150-300 generated instantiations) or the normalization policy that contains it (e.g. widen char operands to a common width at kernel entry rather than N^2 width pairs). Without that ruling, the macro generator quietly becomes the biggest artifact in the codebase.
* The differential test harness is named as an invariant but assigned to no one: kernel path vs generic frame-machine path must produce identical values AND identical representations (d.16 makes representation user-visible through printing), and the scheduler bundle adds 1-worker vs N-worker schedule-invariance testing. This harness is the single cheapest guard on the whole 'recognition is unobservable' doctrine and should be a named v1 deliverable, built before the second kernel exists.
* No consolidated statement of what the seal layer actually needs from v1. Each bundle reserves a different hook — view slot in list headers (dispatch), cache slot on bindings (kernels), watcher callbacks (environments), per-module generations (environments), effect slot (ledger) — with no reconciliation. The minimal true set appears to be: the ledger's reserved binding slots (effect, doc) plus one observable write event (the registry/env generation counter). Someone should write the one-paragraph 'seal substrate contract' so five speculative slots collapse to two real ones.
* No line/scope budget exists anywhere. The ledger's spirit (and this critique's mandate) implies a stated constraint like 'interpreter core excluding kernels stays under ~5k lines; kernels under ~5k more' — the skeleton is 4.6k lines total and proves the semantics fit. Without a written budget, each bundle's 'modest' additions compound unchecked; with one, every stage-2 proposal has to displace something. The budget is the K discipline, mechanized.
* par-each's [P]-override chunking license is recommended (vectorization bundle) but the one-line ledger addendum it asks for is drafted by nobody, and the interaction with `tasks` (does a chunked par-each show ncores tasks or n?) and with cancellation granularity is unexamined. Small, but it's the kind of observable seam that should be settled in the ledger before someone codes the prelude version.

===== CRITIC: soundness =====

OBJECTIONS:
* LATE-BINDING HOLE (dispatch × environments, the worst cross-area contradiction): dispatch stage-2 caches '(generation, resolved binding ref)' at CallWord sites and assumes the generation bumps on EVERY binding write; environments deliberately does NOT bump any version on re-def (re-def = swap the cell interior, 'zero invalidation'; shape version bumps only on name create/delete/uses change). Compose the two as written and a re-def swaps the cell, no generation changes, the guard passes, and the stale resolved body executes — 'redefinition heals callers' silently broken. Ruling needed: caches hold the BindingCell and re-read its interior on every execution (env-area/PyPy-celldict discipline); generations guard only the resolution PATH (shape/uses). Dispatch's '(generation, resolved binding ref)' formulation must be struck or rewritten as '(shape epochs, cell pointer)'.
* MEMORY-ORDERING BUG (kernels vs values/scheduler): kernels says load the refcount 'with Relaxed for the uniqueness test' and attributes this to Swift; values and scheduler correctly require Acquire. Relaxed is unsound: an rc==1 Relaxed load does not synchronize with the Release decrement of a concurrent drop on another thread, so in-place reuse can race with that thread's still-in-flight reads of the buffer. Rust Arc::get_mut and the Boost/Swift refcount doctrine use Acquire (or an acquire fence after the check). Mandate one uniqueness-test function with Acquire ordering, used by kernels, append, dict amend, and view-slot invalidation alike — three bundles currently specify it three ways.
* ESCAPE-PROMOTION ENUMERATION INCOMPLETE (values, reserved option b): the BEAM-style 'unit-local non-atomic RC until the enumerable send points' scheme lists only spawn's cons'd quotation and task outcome cells as escape points. Env binding is a third: d.20 says spawned quotations receive inputs 'via cons or env names', so anything the session thread binds with def/let is readable by every parallel unit; a unit-local value published via binding, still on non-atomic RC, gives a refcount data race. Registry registration ('module') is a fourth. Harmless for v1 atomic RC, but the 'reserved without relayout' claim is false as enumerated — promotion must fire on env/registry writes too, or the option dies.
* SINGLE-WRITER ENV CLAIM OVERSTATED (environments): 'an env table is written only by its owning unit' and 'watchers fire on the owning writer's publish path' hold for session/child envs ONLY because the skeleton runs attempt/spawn/dict-of/combinator bodies in disposable child envs (runtime.rs:1867 and the d.18 addenda tests) — a load-bearing invariant no bundle states. And it does NOT hold for the registry: a spawned quotation can execute `'name (body) module` or trigger `use`-with-ECL_PATH-load, so the registry has genuinely concurrent writers; a clone-and-swap of the registry map without CAS-retry or a write lock loses concurrent registrations, and 'watchers fire on the owner's path' has no owner there. The registry write path needs an explicit multi-writer protocol; the env bundle's own PyDict_Watch-under-free-threading warning applies to its own registry design.
* SNAPSHOT SEMANTICS AS PROPOSED IS ITSELF A LATE-BINDING CHANGE (kernels): the requested ledger ruling 'an isolated combinator resolves its quotation's words once at entry' changes observable semantics for multi-word quotations whose execution re-defs a word the same quotation calls on a later iteration (today: next application sees the re-def). The bundle's own defense covers only single-word quotations. Scope the ruling to the recognition guard alone — guard once, run the fused kernel; on guard failure the generic path keeps per-application, per-occurrence late binding — or explicitly document the semantic change in the ledger. Do not let a performance footnote quietly redefine decision 5.
* FLOAT FOLD RULING: THE TWO BUNDLES DISAGREE AND VECTORIZATION'S OPTION IS UNSOUND AS STATED: vectorization mandates a fixed blockwise association 'shared by every execution path' with the frame-machine fallback 'deferring to the same kernel' — but the generic path exists precisely for unrecognized/shadowed quotations and executes an arbitrary quotation per element left-to-right; it cannot run blockwise. Under the blockwise ruling, `0 (+) fold` recognized vs a near-miss (or a shadow-then-restore of `+`) produce different float answers — recognition becomes observable, violating the invisibility doctrine both bundles rest on. Kernels' option (a) — float folds strictly sequential; only exact/associative reductions (int with overflow masks, min/max) vectorize and parallelize — is the only ruling that keeps fused ≡ generic bit-identical. If the ledger instead blesses blockwise floats, it must redefine fold-on-float-leaf semantics AND make the generic path literally implement the same tree.
* CANCELLATION OF PARKED UNITS + DOUBLE-WAKE (scheduler): cancellation is specified as delivered at safe points of a RUNNING unit, but a unit parked in a task cell's waiter list executes no safe points; cancel must remove it from waiter lists (or poison its wake) and schedule it to unwind. Worse, combined with await-any's 'unregister lazily, stale waiters check the once-flag on wake', a unit can be enqueued by a cell completion AND by cancel — double-enqueue means one unit running on two workers, which corrupts its stacks unrecoverably. Waiter/wake needs a per-unit wake token (CAS'd once per park), not just the per-await-any result flag. No bundle specifies this protocol.
* CHILDREN-LIST RACE (scheduler, internally inconsistent): 'the children list needs no lock: only the owning unit appends and walks it' directly contradicts the same paragraph's 'the cancelling thread walks via the child unit's control block under a small per-task mutex'. If cancel walks a children list the owner is concurrently appending to, an in-flight spawn can miss the cancel flag and become an unsupervised orphan — breaking structured lifetime. Rule: children list under the per-task mutex, AND spawn re-checks the unit's own cancel flag after registering each child (kill-on-arrival).
* INTRA-KERNEL CANCELLATION CONTRADICTION (vectorization vs scheduler/frames/kernels): vectorization says 'cancellation stays at level 3 only: kernel splits are invisible and uncancellable mid-block; a cancelled unit is discarded at the next frame-boundary safe point after its kernel call returns', while scheduler, frames, and kernels all require fuel polls every ~64K elements INSIDE kernels precisely because a multi-GB kernel is one frame step. Under vectorization's rule the BEAM/NIF unbounded-latency problem returns the moment level 2 lands. Reconcile: the coordinating worker polls between blocks and abandons remaining blocks (splits are pure, partial output discarded safely); per-block work stays bounded; and this applies to single-threaded kernels today, not just future splits.
* IN-PLACE REUSE × DEFERRED ERROR CHECK CLOBBERS THE RESCAN SOURCE (kernels + vectorization, unflagged by either): the kernel convention steals a unique input buffer as the output, and overflow detection accumulates a mask checked once per block with a scalar RESCAN of the block to find the failing element. If the block's stores land before the mask test and output aliases input, the rescan reads already-overwritten input — wrong element index or garbage in the error dict's 'data payload. Specify: when output aliases input, test the fault mask BEFORE storing that block (per-vector or per-block), or forgo buffer stealing for checked integer ops.
* TRAILING-SEGMENT PROVENANCE OPTION IS A FOOTGUN (values): storing spans as 'an optional trailing segment in the list header' of reader-produced lists collides with d.1/d.21(b): a reader-produced list that ends up uniquely held (a literal built and consumed in one pipeline) gets slack-capacity append that overwrites the segment or breaks capacity-derived-from-bucket-class arithmetic. Kill the trailing-segment option; side table keyed by list identity only — and note that identity-keyed spans die on CoW copy, so the ledger's 'provenance attached to every token' must be stated as reader-plane, degrade-via-has? (d.22 absence-is-absence).
* LEAF-TAG ENUM DISAGREEMENT (values vs kernels vs vectorization): values amends the leaf set to include symbol leaves (u32 ids); kernels' dispatch enum (I64/F64/Char1/2/4/GenericSpine/Dict) omits them; vectorization's kernel matrix omits them but demands a reserved packed-bool/i8 mask slot kernels doesn't carry. The op×tag dispatch table, kernel registry, idiom table, and printer all key on this enum — freeze ONE enum (with symbol leaf and reserved narrow-mask slots) across areas before any kernel signature is written, or the 'few dozen loops' surface fractures into per-area dialects.
* HOT-RELOAD MID-BODY TEARING NOT PINNED (environments): 'qualified-word execution and module-home resolution do one atomic load of the current generation' — if that load happens per word OCCURRENCE, a public body calling private p1 then p2 can straddle a re-registration and execute p1 from gen N and p2 from gen N+1 (mixed-generation execution; Erlang guarantees whole-version consistency per call). The frames-carry-env-ref design gives whole-body pinning by construction, but no bundle states it as an invariant — state it, so per-occurrence registry loads never get 'optimized' in later.
* PAR-EACH CHUNKING 'PURE OPTIMIZATION' OVERCLAIM (vectorization): serializing elements within a chunk changes liveness, not just interleaving — element quotations can rendezvous (element A awaits a task that only element B's execution publishes via env/task handles); spawn-per-element completes, chunked-serial deadlocks. Either the ledger states par-each guarantees no cross-element progress (elements may run fully serially, making such programs already broken), or the chunked [P] override is not observationally conformant. One line, but it must be written before anyone ships the override.
